# 开发执行参考

角色：Developer Workflow / HOW。本文只给出接口适配、Bugfix 验证、CI 定位、文档验收和 commit / push 的操作步骤。范围与投入判断见[开发范围与效率治理](pra_development_scope_and_efficiency_governance.md)，硬边界与权限以根级 [AGENTS.md](../AGENTS.md) 和用户当前指令为准；按需读取对应节。

## 1. 改 DTO 或接口：查哪些 caller

1. 从变更的函数、DTO、enum、返回结构或持久字段名开始搜索定义与引用，例如 `rg -n '目标符号' app tests`；涉及脚本入口时再覆盖对应 scripts / Adapter。
2. 列出直接生产 caller：构造、参数传递、返回值解包、序列化、持久化和页面展示；动态注册入口按实际配置追踪。
3. 列出直接测试 caller、fixture、mock 和断言，连同生产 caller 一次适配。
4. 保持原业务断言，再验证直接受影响的调用链；不通过迁就实现的预期值掩盖回归。

## 2. Bugfix：跑哪些测试

按“有效失败证据或最小复现 → 修复 → 原失败用例 → 同根因直接回归 → 必要集成”执行。

| 改动对象 | 操作 |
|---|---|
| 文档 / 文案 | 执行第 4 节的编码、差异、链接和直接语义检查 |
| 纯函数 / 格式化 / 映射 | 用轻量参数化用例覆盖受影响边界 |
| 接口 / DTO | 更新直接 caller 与 fixture，跑受影响用例及直接调用链 |
| 授权 / 持久化 / 事务 / 并发 / UNKNOWN / 恢复 | 使用真实临时 Runtime，覆盖受影响的授权绑定、幂等、原子性、失败和重启路径 |

本地开发统一使用项目环境，例如 `& .\.venv\Scripts\python.exe -m pytest -q tests/目标文件.py::目标用例`；静态检查使用 `& .\.venv\Scripts\python.exe -m ruff check 目标文件`。正常结果保留摘要，失败时保留对应断言和堆栈。完整 Gate 的适用时机见治理文档。

## 3. CI failure：怎么定位

1. 按治理文档确认该失败属于本轮范围，并核对 run 的 Head、workflow、job 与当前版本。
2. 成功只读状态和必要步骤摘要；失败先读失败 job、stack 或直接相关 artifact，再读取涉及的测试与实现片段。
3. 区分实现缺陷、测试缺陷、fixture 时间/顺序不一致、环境差异与已证实的偶发故障；先做最小诊断，再定向复现。
4. 实现或测试缺陷：完成对应修复，跑原失败与直接回归；稳定候选判断适用 Gate，主动执行完整 Gate 仍须遵守根级 `AGENTS.md` 的资源授权约束。用户当前请求已经明确要求相应完整验证时，复用该授权，不再次询问。
5. 外部环境故障：记录故障原因、恢复依据及源码/测试/依赖/配置版本；可以在相同版本上重跑，但 Agent 主动重跑前必须按根级 `AGENTS.md` 重新取得授权。保留原失败和重跑结果，不把单次转绿当作根因证据。
6. 比较复用证据所绑定的源码、测试、依赖、配置与环境，记录差异及覆盖范围，不把历史成功改写成新 Head 的结果。

需要调整 CI 分层时，在对应工作流任务中实施：去除相同环境和输入下被全量覆盖的重复子集，保留具有平台差异、隔离或恢复目的的检查；本文件不改变既有触发条件或 Gate。

## 4. 文档：怎么验证

1. 写前检查目标文件是否被占用。普通文本显式使用 UTF-8；CSV/TSV 使用 UTF-8-SIG；bat 使用 ASCII + CRLF。
2. 含中文文件写后严格回读，核对首行并抽查 1 至 3 行中文；表格核对表头与样例，JSON 解析后检查关键字段。终端显示不能替代文件验收。
3. 检查局部 diff、相对链接、角色边界及直接语义冲突，再运行 `git diff --check`。历史原样 archive / hash-bound evidence 保持原字节，不批量整理。
4. 进度写入 `project_current_status.md`；`index.md` 只更新路径、标题与文档角色，不复制阶段状态、验收结果或待办。
5. 校对 Current Status 与 PR 正文的版本、已完成项、验证范围和直接未完成项；已知失败必须如实记录。

## 5. commit / push：怎么组织

1. 核对 branch / worktree 与已有改动，沿用用户有效授权和明确的提交、推送时机。
2. 开发中允许小步 commit，相关修改与验证完成后集中交付；必要记录写入已有主文档，历史报告保持其版本身份。
3. **每次 Codex 推送前，都同步更新 `docs/project_current_status.md` 并纳入待推送提交，包括纯文档推送。** 记录本批改动、当前阶段、已完成验证和直接下一步；业务阶段未变时也写明本批文档或测试进展，不只改日期。
4. 状态页和报告绑定已有实现/测试版本及已完成 CI；待推送版本的 CI 如实写为待运行或待完成。文档不记录自身尚未生成的 commit SHA，最终 PR Head 在提交后写入 PR 正文，避免自引用提交链。
5. 验收文档后检查暂存 diff，仅提交本轮相关文件；推送前确认 Current Status 已覆盖整批待推送改动。
6. 推送后核对远端 PR Head，同步 PR 正文的改动、版本、验证与剩余事项；新 Head CI 按当时实际状态记录。后续 CI 结果可更新 PR 正文，下次推送前再同步状态页，不为记录自身 SHA 反复提交。
7. 最终简述本轮结果、验证和实际提交/推送状态。合并、结束 Draft、部署和真实平台操作仍须对应授权。
