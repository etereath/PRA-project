# PRA 开发范围与效率治理规范

角色：Developer Governance / WHY & WHEN。本文只定义阅读与修改范围、扩大范围的条件、不处理的问题、完整 Gate 的适用时机和停止条件。操作步骤统一放在[开发执行参考](development_workflow.md)，产品实际边界优先见 [Owner Product Boundary](owner_product_boundary.md)，硬边界与权限以根级 [AGENTS.md](../AGENTS.md) 和用户当前指令为准。

项目进度由[当前状态](project_current_status.md)维护；[索引](index.md)只提供文档导航，不保存进度。状态页只在阶段、范围、blocker、验收结论或其他影响下一位开发者判断的事实发生实质变化时更新；即时 Head 与 CI 以 GitHub 为准。

## 1. 产品复杂度预算

PRA 当前服务约 10 人的家庭农场，实际管理者不超过 3 人；一个部署实例中，每个平台只有一个受控经营账号；目标正式客户端为微信小程序 + PRA 后端 API。它不是 SaaS、多租户或企业通用平台。

因此：

- 理论上的未来企业需求、多账号、多租户、组织分工、值班升级或复杂网络模型不构成当前施工理由；
- 现有 `account_id` 只能作为兼容实现字段继续存在，不得继续扩散成经营 scope、qualification scope、Queue blocker scope 或新的 session/page identity 体系；
- 不建设 active session/account binding、page identity proof、Review owner claim/转交/escalation、企业 IAM 或第二套正式客户端身份系统，除非负责人明确批准新的真实业务需求；
- 不同平台的 Adapter / Executor / ShadowBot 差异本身提供运行隔离；真实写安全由商品读取、expected old 比较、执行和写后回读保证；
- 用户决定、执行责任、当前平台事实、历史证据必须分别建模，不能为了让四者“完全一致”而新增长期 blocker 或证明层。

新增任何表、字段、Service、daemon、Queue、状态机、blocker framework、认证层或兼容层前，必须回答：

1. 当前家庭农场如果不加，会发生什么具体业务事故？
2. 现有 Task / operation / attempt / write lock / v4/v5 / Queue / Worker / Importer / Review/Outbox 为什么不能承担？
3. 新结构的明确退役条件是什么，还是它确实是长期业务能力？

不能回答则不施工。

## 2. 读多大范围，以及为什么

阅读投入以能改变当前任务判断的证据为限。起点是根级 AGENTS、Owner Product Boundary、当前状态、用户指定对象、相关版本以及直接受影响的实现；同一任务后续复用仍有效的基线，只读增量。

- 产品目标或业务定义不清时，读取对应业务主文档。
- 修改涉及公共合同、持久状态或组件责任时，覆盖其直接依赖链。
- 已有证据覆盖相同源码、测试、依赖、配置和等效环境时，允许复用；影响结论的变化才要求补充证据。
- 仓库规模、父任务规模和历史材料数量，不构成扩大阅读范围的理由。
- 开发任务不自动切换为全项目审核。明确要求审核时，范围仍以用户指定对象为准。
- 接受审核任务不自动启用归档规范；`.archive/` 材料须由用户在当前请求中明确点名，才可读取或使用，不通过开发入口间接导入。

## 3. 何时扩范围

只有实际影响或新证据构成直接依赖时，才扩大到相应范围。

| 触发条件 | 必要关注范围 |
|---|---|
| 真实平台写或其授权行为改变 | 主体与范围、写前比较、写后回读、幂等和 UNKNOWN 处理 |
| Schema、持久状态、lock 或 authority 改变 | 当前 owner、原子事务、重启恢复与权威唯一性 |
| 公共接口、DTO、enum 或持久字段改变 | 直接生产与测试调用链、数据合同 |
| 跨组件职责或恢复路径改变 | 受影响的完整业务交接与终态责任 |
| 同根因直接影响入口、修改引入的回归、妨碍修复的结构缺口 | 完成当前修复所必需的直接整改 |
| 新证据明确破坏硬安全边界 | 相应安全处置与必要验证，不扩大真实操作权限 |

CI 失败仅在阻碍当前目标、由当前修改直接引入，或属于用户明确授权的 CI 整改时，进入本轮处理范围。普通文档评阅不因存在无关失败而转向 CI 排查。

新增表、Service、daemon、Queue、状态机或兼容层，须有具体业务事故与既有能力不足的依据。现有结构能承担责任时优先复用；理论上的未来用途不构成扩建理由。边界阻碍目标时显式说明冲突，不能通过旁路扩大授权。

### Blocker 扩大门禁

默认 blocker 应作用在能够防止具体事故的最小范围，例如单 Task、单 SKU/action 或单平台真实写。历史对象、单 SKU UNKNOWN、单 Review、旧 pending Task、单次 READ_ONLY 失败或局部内部数据异常，不得自动扩成整个平台或跨平台停止。

如果开发者认为必须新增或扩大到“整个平台写队列、跨 SKU、跨平台、READ_ONLY/recovery”级别的 blocker，必须先停止施工并提交短 Proposal，说明：

- 触发条件；
- 不扩大 blocker 会发生的具体事故；
- 为什么 SKU/action 层不足；
- 实际阻止哪些动作；
- 哪些 READ_ONLY / reconcile / diagnostics 仍允许；
- 自动释放和人工恢复条件。

旧 GQB-1～GQB-4 可作为历史风险分类参考，但不是必须继续扩建的通用 blocker framework；不得因为历史合同存在这些术语，就主动增加第五类或新的 blocker Service。`account_id` 不再作为 blocker scope。

## 4. UNKNOWN 与人工恢复的复杂度边界

UNKNOWN / NEEDS_RECONCILIATION 不得猜测成功或失败，也不得第二次不安全写。优先使用既有唯一 RECONCILE。

但人工恢复必须能够处理“自动恢复本身失败”的场景，不得要求自动 RECONCILE 必须先留下完整标准回执，人工才有资格介入。

允许的最小人工兜底语义是：

```text
旧真实写/对账已经停止
+ 旧 Queue 请求不会再次被消费
+ stopped boundary 之后取得可信当前平台事实
→ 可以终止旧 one-shot 当前责任
```

同时：

- 不能仅凭超时释放写锁；
- 不能把当前事实倒推成历史 click 成功或失败；
- 历史 side effect 可以永久保持 UNKNOWN；
- 任一有权限管理员可以处理，记录实际处理者即可，不默认建设 claim/转交/escalation 工作流；
- 结束旧责任不要求恢复历史 Queue 绝对路径、applet URI 或执行 profile；继续执行旧授权时才需要核对适用运行环境。

## 5. 授权与执行前验证分离

用户授权的业务含义与执行端实时校验必须分开。

用户授权应聚焦真正改变经营决定身份的内容，例如：

- 平台商品 / internal SKU；
- action；
- expected old；
- target；
- 有效期；
- 必要业务范围和人工主体。

扫描时间变化、无关库存版本、其他 SKU 主数据变化、Queue 目录、applet URI 等不应自动把同一个经营决定变成“另一个授权”。这些内容可以作为执行环境或审计信息，但不能无条件进入用户决定 identity。

执行端仍必须在副作用前实时读取并比较 expected old；不一致就 zero write；执行后重新读取确认。复杂度收缩不得放松这一硬安全链。

目标已经被可信当前事实满足时，本质是“结束旧 one-shot 的本地受控状态变更”，不默认要求准备完整平台写 batch、execution continuation 和 Coordinator 旅程。

## 6. 什么问题不处理

- 独立于当前目标的历史文档错误、其他模块 warning、无关测试失败、旧架构债务和其他平台缺陷，不自动加入本轮任务或完成条件。
- 既定整改清单之外的可讨论问题，不自动成为新 blocker；必要时简短记录为后续项。
- 已由用户或有效状态记录关闭的阶段与问题，不反复重开；只有新证据直接冲突时才重新核验。
- 开发者不自行重复审核端对整个阶段的裁决，也不将 Reviewer checklist 变成普通开发前置条件。
- 小修不默认新增长报告；新业务能力、迁移、复杂恢复、实机验收或重要故障需要长期证据时，才建立专门报告。
- 为了“清理历史过度开发”不得顺手大规模删除 schema 字段、迁移保护或现役入口；先停止业务依赖，再删生产代码，最后才判断物理 schema cleanup 是否值得。

## 7. 何时需要完整 Gate

稳定候选需要判断与改动风险相匹配的适用 Gate；是否主动运行完整 Gate 仍受根级 [AGENTS.md](../AGENTS.md) 的资源授权约束。用户当前请求已明确要求相应完整验证时复用该授权，不重复询问；开发中的局部反馈采用与影响匹配的定向验证。资源预算不得降低授权、持久化、事务、并发和恢复所需的真实临时 Runtime 集成证据；所需验证超过预算时先申请扩大范围，未获授权不得将定向结果写成完整 Gate 已通过。

- 源码、测试、依赖、配置或环境发生影响结论的变化，或存在尚未解除的相关风险时，重新判断适用的完整 Gate。
- 相同输入与等效环境已有完整 CI 证据时，不为形式重复本地全量。
- 同一环境中完整 pytest 已覆盖的测试子集不应再次机械重跑；只有平台差异、隔离价值或恢复价值明确时保留独立 Gate。
- 仅 Markdown 变化不自动要求重新验证源码逻辑，也不自动授权调整 CI 工作流。
- 仓库自动触发的 Gate 仍按其实际结果记录，不能绕过；CI 通过不能替代受控实机、部署或长期运行证据。
- 相关 CI 失败须有原因和验证依据才可收口；已证实并恢复的外部环境故障可以在同版本重跑，不要求制造仓库改动，但 Agent 主动重跑前必须按根级 `AGENTS.md` 重新取得授权。执行步骤见开发执行参考。

## 8. 文档与状态维护成本

GitHub PR Head、commit、CI 是即时版本事实。`project_current_status.md` 只在以下内容发生实质变化时更新：

- 阶段开始/结束；
- 当前施工范围变化；
- blocker 新增/关闭；
- 验收或 Stage Goal 结论变化；
- 会影响下一位开发者判断的 authority、部署或运行状态变化。

不再要求：

- 每次微小 push 都改状态页；
- 纯文档 SHA 为了记录自身再次产生新文档 commit；
- PR 正文和状态页反复追逐同一个 Head/CI 数字。

历史报告保留其版本身份，不为“当前化”反复重写。

## 9. 什么时候停止

用户指定目标完成、原问题与直接回归验证通过、必要集成及本次适用交付门禁满足后，应结束本轮工作，不继续寻找无关问题。

- 已知且直接阻碍当前交付的失败仍属于本轮任务，不能仅因“状态已明确”宣告完成。
- 用户明确限制本轮只做诊断、一次 CI 或指定步骤时，达到该范围即停止，并如实保留未完成项；不把失败写成通过。
- 等待人工授权、现场验收或其他外部依赖时，记录实际负责者、下一触发与所需证据，不能靠扩大代码或审核范围替代。
- 文件编码、隔离测试、CI、实机与部署是不同证据；阶段状态只依据相应裁决和证据更新。
- 本轮交付完成后，新的独立审核或开发目标需要新的任务范围。
