# PRA 开发范围与效率治理规范

**角色：Developer / Execution Governance**  
**适用对象：Codex 及其他承担 PRA 实现、修复、测试和交付工作的开发 Agent**

本规范管理开发过程中的阅读范围、注意力投入、修改范围、测试与 CI、文档产出、工具调用和停止条件。

目标不是让开发 Agent 对整个项目进行完整审核，而是：

> **用最少的必要上下文和验证投入，正确完成当前被授权的开发任务，并保持关键业务与安全边界。**

任务硬边界与权限以根级 [`AGENTS.md`](../AGENTS.md) 和用户当前指令为准；具体测试操作可按需读取 [`development_workflow.md`](development_workflow.md)。

---

## 1. 开发端与审核端分离

开发 Agent 的默认职责是：

> 理解当前任务 → 定位直接实现 → 修改 → 验证 → 交付。

除非用户明确要求当前 Agent 承担审核任务，否则开发过程中默认：

- 不执行完整项目审核；
- 不自行建立或扩大 P1 / P2 blocker；
- 不重新判断整个阶段是否 PASS；
- 不为了寻找潜在问题扫描整个仓库；
- 不读取 Reviewer 专属审核规范；
- 不把审核方法、审核严重度或 Reviewer checklist 转化为开发前置条件。

`pra_review_risk_and_complexity_governance.md`、`.archive/web-review/**` 以及其他明确标记为 Reviewer / Review Governance 的材料属于审核端参考，不是 Codex 默认施工输入。只有用户当前明确要求审核、架构重审、完整实现重新评估或治理规范维护时，才进入对应审核流程。

---

## 2. 新任务从最小上下文开始

新会话或新任务首先只建立最小施工基线：

1. 根 `AGENTS.md`；
2. `docs/project_current_status.md`；
3. 用户明确指定的 Issue / PR / Goal / 文件；
4. 当前 branch / worktree / Head；
5. 本任务直接修改的源码、文档或测试。

先回答：

- 当前要完成什么？
- 当前允许修改什么？
- 当前直接入口在哪里？
- 什么证据足以证明这个开发任务完成？

不要因为仓库中存在大量设计、历史、报告和测试文件就默认全部读取。

---

## 3. 按直接依赖扩展，不按仓库规模扩展

阅读范围沿当前改动的直接依赖链扩展。

修改函数、DTO、enum、返回结构或持久字段时，优先检查：

```text
目标定义
→ 直接生产 caller
→ 直接测试 caller
→ 必要的数据合同 / 持久状态
```

修改跨组件业务流程时，只追踪受影响的正式箭头，例如：

```text
Web
→ Runtime
→ Queue
→ Worker
→ Importer
→ Terminal
```

只有发现真实依赖后才继续向外扩展。

默认不要：

- 通读整个 `app/`；
- 通读整个 `tests/`；
- 阅读全部历史 reports / plans；
- 重新拉取已经建立基线的完整 PR 历史；
- 从项目第一阶段重新建立完整架构认知；
- 为一个局部 bug 探索所有平台和所有业务动作。

---

## 4. 只有明确触发条件才升级范围

### 4.1 真实平台副作用

涉及 UPDATE_PRICE、SET_ONLINE、SET_OFFLINE 或其他真实写时，继续检查正式授权、写前读取、expected state compare、写入、写后回读、幂等和 UNKNOWN 处理。

### 4.2 持久状态或 authority

涉及 Schema、migration、Task 状态、operation、continuation、lock 或 authority 时，继续检查当前 owner、事务边界、重启恢复和既有结构复用。

### 4.3 公共接口合同

涉及函数签名、DTO、enum、返回结构、公共 helper 或持久字段时，搜索直接生产 caller 与直接测试 caller，并一次同步适配。

### 4.4 跨组件责任

如果修改改变组件间责任或恢复箭头，验证受影响的完整箭头；不因为存在理论风险自动扩大到无关组件。

---

## 5. 已确定的问题集合不得自行扩张

如果任务来自 Reviewer blocker、用户指定 bug、PR comment 或明确整改清单，以该问题集为主要施工范围。

修复过程中只额外处理：

1. 当前修改直接造成的回归；
2. 当前问题无法修复所暴露的直接结构缺口；
3. 明确破坏根级硬安全边界的问题。

其他独立问题可以简短记录，但不自动加入当前任务、不暂停当前施工、不重新设计整个模块。

开发 Agent 不因为“又发现一个可讨论的问题”而切换成无限审核模式。

---

## 6. 开发期采用最小充分验证

默认开发循环：

```text
原问题复现
→ 最小修复
→ 原问题测试
→ 直接回归
→ 必要集成
```

不要把每次小改动都变成完整仓库验收。

- 文档 / 文案：编码回读、diff、链接和直接语义冲突；
- 纯函数 / 格式化 / 映射：轻量参数化测试；
- 接口 / DTO：生产 caller、测试 caller 与直接集成；
- 授权 / 持久化 / 事务 / 并发 / UNKNOWN / 恢复：真实临时 Runtime 的必要集成。

具体执行表见 [`development_workflow.md`](development_workflow.md)。

---

## 7. 完整 Gate 只用于稳定候选

完整 CI 的职责是验证稳定候选版本，不是作为每次编辑后的开发反馈循环。

开发过程中：

1. 优先运行定向测试；
2. 先解决已知失败；
3. 形成稳定 candidate；
4. 再 push 并运行适用完整 Gate。

如果 GitHub CI 已在相同源码、相同测试和等效环境覆盖所需全量，不为了形式再本地重复完整全量。已有仓库 Gate 仍由 Gate 自身决定结果，不人为绕过。

---

## 8. CI 失败必须定位，不能靠重跑碰绿

CI 失败后先判断：

```text
实现缺陷？
测试缺陷？
fixture / 时间 / 顺序不一致？
环境差异？
真实 flaky？
```

优先读取失败 job、失败 stack 和直接相关测试，并用定向复现定位原因。

禁止把一次失败改写成“未验证”，也禁止只靠重复运行直到绿色宣称问题解决。只有找到原因、做出对应修改并验证修复后，后续完整 CI 成功才构成有效收口证据。

---

## 9. 已验证证据允许复用

相关源码、测试、依赖、配置和环境未发生影响结论的变化时，可以复用已有验证。

例如源码与测试已经在 Windows / Linux 完整通过，后续 Head 只修改 Markdown，则不需要在本地重新证明源码逻辑；如果仓库自动 Gate 因新 Head 再运行，仍以新 Gate 的实际结果为准。

同一任务已经建立版本和调用链基线后，后续只重新读取：

- 新 commit / changed files；
- 新 PR comment；
- 新 CI；
- 受影响的源码 / 测试 / Canonical 片段。

内容和 SHA 未变化的材料不机械重读。

---

## 10. 文档、工具与 Token 有成本预算

### 文档

开发过程不为每个小修建立独立长报告。普通修复优先通过 commit message、PR body、必要测试和最终交付摘要记录。

只有新业务能力、migration、复杂恢复路径、实机验收、重要故障分析或未来维护确实需要长期证据时，才新增正式报告。

不要形成“修一行 → 新报告 → 更新 index → 更新报告里的 Head → 再提交 → 又更新 Head”的自引用提交链。

### 工具

- 优先一次搜索符号定义、生产 caller 和测试 caller；
- 优先局部 diff、目标函数和直接测试片段；
- CI 成功读取状态与步骤摘要即可，失败再读取日志；
- 已建立 PR 基线后只读增量，不反复拉取完整历史；
- 减少无变化轮询和重复输出长文件。

Token 应投入真正可能改变当前实现或验证结论的材料。

---

## 11. 新复杂度必须证明事故

新增表、Service、daemon、Queue、状态机、version、lock 或 compatibility layer 前先回答：

> 如果不增加它，当前真实业务会发生什么具体事故？

如果现有结构已经能够表达状态、保存责任、恢复和审计，优先复用。不能因为“以后可能用得到”提前扩建通用框架。

---

## 12. 不主动修复无关问题

当前任务之外发现历史文档错误、其他模块 warning、无关测试问题、旧架构债务或其他平台缺陷，只要不阻止当前目标：

- 不自动修改；
- 不自动扩大 PR；
- 不自动加入当前完成条件；
- 可以在交付摘要中简短记录为后续项。

已由用户、当前状态或当前任务明确的阶段、平台、范围和已关闭问题，不反复重新确认；只有新证据与既有事实直接冲突时才重新核验。

---

## 13. 开发停止条件

当满足以下条件时，应停止继续扩张当前任务：

1. 用户指定目标已实现；
2. 原问题或目标测试通过；
3. 直接回归通过；
4. 必要集成通过；
5. 当前适用 CI / Gate 已满足，或其状态已明确；
6. 当前修改没有造成新的硬边界破坏；
7. 交付状态能够清楚说明。

不要继续“顺便再看看整个系统还有没有别的问题”。那属于新的审核或新的开发任务。

普通开发交付只需简要说明：

```text
Goal     完成了什么
Changed  修改的核心文件 / 行为
Validation  定向测试与适用 CI
Remaining   只列与当前目标直接相关的未完成事项
Head     当前提交 / PR Head
```

无需模拟审核端输出 P1、P2、Review Profile、Stage Goal 或全项目风险表，除非用户明确要求当前 Agent 承担审核职责。

---

## 核心原则

> **先完成当前真实任务，再扩展必要依赖。**

> **按影响扩大上下文，不按项目规模扩大上下文。**

> **开发 Agent 负责实现，不自行重复审核端工作。**

> **用定向测试获得快速反馈，用稳定候选的完整 Gate 获得交付证据。**

> **已经证明的事实可以复用，已经结束的任务应当停止。**

开发效率不是减少正确性，而是把注意力和验证资源投入真正可能改变当前结果的地方。
