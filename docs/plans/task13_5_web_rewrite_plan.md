## 1. 结论

当前 Web 已经具备任务、复核、通知、执行记录、业务输入和系统检查等功能入口，但页面
仍然按照开发过程和数据库结构组织，而不是按照运营人员的工作顺序组织。重写工作的
重点不应只是更换颜色或调整卡片，而应同时完成：

1. 从“数据表和脚本入口”转为“今日运营、待办、自动化、异常、销售和审计”。
2. 将运营摘要与工程诊断分层，默认页面不再暴露合同字段、hash、phase、内部枚举和
   结果 JSON。
3. 将任务列表、详情、复核、异常和执行记录连接成一个连续的处置流程。
4. 将只能通过命令行运行的自动规则和扫描流程收口到独立的“自动化”模块。
5. 对列表密度、详情路由、分页、响应式和页面体积设置可验证的工程门禁。
6. 保留任务 12/13 已验收的后端动作链路，不让 Web 直接拼装或绕过执行合同。

## 3. 浏览发现

### 3.1 全局导航和页面框架

当前顶部导航包含“首页总览、任务中心、复核中心、通知中心、执行记录、业务数据、
生成待处理任务”七个入口。

主要问题：

- 页面按技术模块平铺，没有“自动化中心、异常中心、销售分析、系统运维”等运营入口。
- “生成待处理任务”被提升为全局一级导航，但它实际是任务中心中的一个上下文操作。
- `/system` 没有出现在全局导航，只能从业务数据页间接进入。
- 每页重复大标题、长说明、导航和登录工具条，首屏有效业务信息偏少。
- 页面标题和正文标题经常重复，例如首页、任务中心和复核中心均出现两次同名标题。
- 当前字体和大尺寸 hero 更像展示页，不适合高频运营后台的密集信息阅读。
- 390 像素宽度下导航占约 169 像素高度，“生成待处理任务”单独占一整行，用户需要
  滚动后才能看到主要工作区。
- 没有统一的面包屑、页面级操作区、全局搜索、数据新鲜度或环境标识。

### 3.2 首页总览

当前首页展示：

- 待复核 13
- 即将超时复核 0
- 失败通知 14
- 待执行任务 20
- 已过期 31

主要问题：

- 指标是数据库状态计数，不是“今天需要做什么”的运营工作台。
- 没有区分测试数据、历史数据和当前生产运营数据。
- 没有扫描新鲜度、最近成功时间、Worker 健康、自动化计划或异常严重度。
- 没有销售额、销量、订单数、缺货、上架状态变化等经营信息。
- “失败通知”和“待执行任务”只有数量，没有影响、优先级和下一步动作。
- “已过期”同时混合任务和复核，需要用户再次选择两个入口。
- 首页没有明确回答“系统现在是否可以继续运行”。

### 3.3 任务中心

当前数据库中展示 146 条任务，默认每页 50 条。任务表包含 12 列；桌面快照宽约
1335 像素、页面高 5330 像素，390 像素移动视口下表格宽约 1239 像素、页面高
6844 像素。

主要问题：

- 人工任务、自动规则任务、真实平台任务、历史测试任务和故障注入任务混在同一列表。
- “规则任务组 ID、任务组状态、任务状态”同时占据主列表，运营人员不容易判断真正
  需要处理的状态。
- 页面直接展示 `online / offline`、`default_platform`、
  `WINDOW_NOT_AVAILABLE`、`PRODUCT_LIST_REFRESH_FAILED` 等内部值。
- 部分历史数据出现 `???????`，但页面没有把它识别为数据质量异常。
- 任务详情附加在完整 50 行列表之后，查看详情仍需要先下载和滚过完整列表。
- 详情默认展示幂等去重键、内部 SKU、decision trace、截断 JSON、关联表技术字段。
- 缺少来源、通道、业务优先级、影响范围、推荐动作和异常归属。
- 缺少常用视图，例如“今天待办、我负责的、自动任务、人工任务、结果未知、已过期”。
- 默认 50 行过多，且没有列选择、密度选择、保存筛选或快速搜索。

### 3.4 复核中心

当前展示 53 条复核，默认每页 50 条。

主要问题：

- 复核类型直接出现 `listing_location_anomaly`、
  `shadowbot_login_verification`、`shadowbot_update_price` 等内部枚举。
- 处理对象显示 `platform_listing：平台|page:...|name:...|grade:...` 等复合业务键。
- 原因中混合中文、英文和内部批次 ID。
- 当前列表混合待处理和大量历史已处理记录，运营人员的当前工作不突出。
- 详情页继续附带完整列表，页面层级不清。
- 处理表单要求选择结果状态、填写备注并直接编辑“结果 JSON”；结果 JSON 不应成为
  运营人员的常规输入。
- 没有把“为什么需要处理、可选动作、每个动作后果、截止时间、相关证据”集中展示。
- 未形成“认领—处理—结果确认—后续状态”的工作台体验。

### 3.5 通知中心

当前展示 41 条通知记录。

主要问题：

- 发送取消但未实际投递的通知可能仍以“发送失败”呈现，运营语义不够准确。
- `unconfigured`、内部 Review ID 和英文错误原因直接出现在主列表。
- 筛选要求用户知道“关联复核任务 ID”，不符合运营查找习惯。
- 通知正文在列表中占据大段空间，影响扫描效率。
- 页面只有查看，没有“安全重试、查看关联待办、确认配置问题、归档噪声”等处置入口。
- 通知问题和业务异常没有统一关联，用户需要在多个页面反复跳转。

### 3.6 执行记录

这是当前最需要治理的页面。

桌面快照页面高度 31704 像素。数据库与顶层执行表为 32 条执行日志，但每条均递归
展开原始输出，形成 32 个嵌套表和 684 个后代行；不得把 684 误写成数据库日志数。
表头中 operation、attempt、hash、queue phase 等字段被大量重复。

主要问题：

- 运营摘要、执行批次、逐商品结果、底层 attempt 和原始诊断没有分层。
- 默认页面平铺 `operation_id`、`execution_attempt_id`、`shadowbot_run_id`、
  `instruction_hash`、文件校验和、队列路径和合同版本。
- 原始输出形成多层嵌套表，页面体积和 DOM 数量随历史记录快速增长。
- 没有先展示“执行了什么、成功几项、失败几项、哪些结果未知、需要谁处理”。
- 缺少按动作类型、平台、结果、时间、来源运行和异常类别筛选。
- 没有将 UNKNOWN 和 RECONCILE 组合成一个业务时间线。
- 技术人员需要的诊断信息是有价值的，但必须移到按需加载的高级诊断区。

### 3.7 业务数据

业务数据页已经具备录入库存、上架状态、价格规则、上下架规则、包装产能和冷库状态
六个页签，是当前相对接近运营流程的页面。

主要问题：

- 页签 URL 携带运行库和多个 Excel 文件的本地绝对路径，URL 过长，也增加误传路径的
  风险。
- 商品列表为每条商品同时在 DOM 中渲染完整编辑表单，数据量增长后页面会变重。
- “商品、库存、规则、产能、冷库”被放在同一一级页，概念跨度较大。
- 上架状态主列表中的来源显示 `shadowbot_sync_status`，仍是内部实现名。
- 没有明确显示数据最后同步时间、新鲜度、是否完整以及与平台的差异。
- “进入 Excel 表格管理”与日常表单入口的适用场景没有充分区分。

### 3.8 任务生成

主要问题：

- 页面仍显示“原 `/` 页面中的任务生成流程已迁移到 `/task-generator`”等开发迁移说明。
- “使用 Mock AI 定价建议”出现在常规业务生成流程中，容易与正式能力混淆。
- 生成模式、规则选择、库存策略等字段缺少面向业务结果的预期说明。
- 缺少生成前影响范围摘要、候选数量、冲突数量、数据新鲜度和安全门禁。
- 它应成为任务中心中的“新建/生成候选任务”流程，而不是全局一级模块。

### 3.9 自动规则与测试台

自动规则页面直接说明：

> 第一版仅展示记录，不提供 apply 按钮；apply 只能通过命令行执行。

这证明当前 Web 尚未承担自动化运维责任。

主要问题：

- 没有调度计划、最近运行、下一次运行、运行耗时、失败原因或手工补跑。
- 没有 small scan、full scan、订单同步、日结、规则评估、通知 Worker 的统一视图。
- Mock 平台测试台放在任务中心的同级页签中，容易与真实运营任务混淆。
- 测试台和真实环境没有明显的环境色、标签和数据隔离提示。

### 3.10 系统维护

系统维护页具备配置、schema、表计数、运行状态和外部连通性检查，但页面高度约
5000 像素。

主要问题：

- 所有检查结果一次性平铺，正常项和异常项没有优先级。
- 没有服务级健康状态、最近成功时间、队列积压、磁盘、备份和证据保留状态。
- “发送飞书测试通知”属于会产生外部效果的操作，但缺少显著的环境和目标说明。
- 页面没有出现在全局导航。
- 技术字段与运营健康摘要没有分层。

## 4. 用户角色和默认视角

### 4.1 运营人员

主要目标：

- 查看今日待办、销售和异常。
- 维护商品、库存和规则。
- 处理复核和可安全恢复的异常。
- 查看任务是否执行成功。

默认隐藏：

- hash、phase、contract、queue path、原始 JSON、数据库表名。

### 4.2 运营负责人

主要目标：

- 查看整体运行、销售趋势、超时、异常和人员待办。
- 暂停或恢复只读自动化计划。
- 审核日结修订和高风险业务动作。
- 查看操作审计。

### 4.3 系统管理员/开发排障人员

主要目标：

- 查看 Worker、队列、Outbox、数据库、迁移、证据和原始合同。
- 执行受控诊断、通知测试、备份恢复和安全补跑。

高级诊断权限不能改变普通写任务的正式授权边界，也不能绕过版本化
`SYSTEM_EMERGENCY` 策略、二次观察、禁止条件、v5 写动作和唯一 RECONCILE。

## 6. 页面重写方案

### 6.1 应用框架

桌面端采用：

- 固定左侧导航。
- 顶部环境、平台交易日、卖家作业日、当前阶段、数据新鲜度和用户区域。
- 页面标题、简短状态说明和右侧主操作。
- 主内容最大宽度和可控密度。

移动端采用：

- 紧凑顶部栏。
- 抽屉式导航。
- 底部只保留“今日运营、待处理、自动化、更多”四个高频入口。
- 数据表按运营重要性转换为卡片或允许选择显示列。

不再在每页重复大面积 hero。

### 6.2 今日运营

首屏按优先级显示：

1. S4/CRITICAL 和 S3/HIGH 异常。
2. 即将超时待办和人工介入。
3. 平台交易日、卖家作业日、当前阶段和 18:00/20:00 倒计时。
4. 自动化、Worker、队列健康和最近成功时间。
5. 销量、卖家实收金额、事实来源和数据质量。
6. 18:00–20:00 下一交易日早期销售。
7. 在线商品状态、价格库存变化和最近执行结果。

每张卡片必须包含：

- 数量或结果。
- 数据截止时间。
- 是否完整。
- 影响范围。
- 唯一明确的下一步。

### 6.3 任务中心

列表默认字段：

- 任务摘要。
- 商品/范围。
- 平台。
- 来源：人工、自动、系统紧急或系统恢复。
- 当前状态。
- 优先级。
- 截止时间。
- 下一步。

规则：

- 默认每页 20 或 25 条。
- 测试数据和真实运营数据使用环境标签和默认隔离。
- 内部 ID 只在详情复制区显示。
- `online/offline` 显示为“上架/下架”。
- 技术错误码映射为中文摘要，原始代码在高级诊断中保留。
- 列表详情使用独立详情页或侧边详情，不再附在完整列表底部。
- 详情按“业务摘要—状态时间线—关联复核—执行结果—高级诊断”排列。
- 使用 `origin_type/origin_ref_id/approval_policy/policy_version` 判断来源和授权，不根据
  `created_by` 字符串猜测。

### 6.4 待办与复核

复核详情首先展示：

- 为什么需要人工处理。
- 影响哪些商品、订单或任务。
- 截止时间和超时后果。
- 平台事实和系统建议。
- 可选择的业务动作及其含义。

表单规则：

- 不允许运营人员直接编辑结果 JSON。
- “调整”使用结构化业务字段。
- 高风险动作显示影响确认摘要。
- 提交后展示状态变化和下一步。
- 支持认领、备注、转交和查看相似异常。

### 6.5 自动化

计划列表展示：

- 计划名称。
- 是否启用。
- 运行时间/间隔。
- 上次成功。
- 当前状态。
- 状态只使用 `RUNNING / SUCCESS / FAILED / MISSED / MERGED / SKIPPED`。
- 下次运行。
- 连续失败次数。
- 数据新鲜度。

`FULL_MARKET_SCAN` 详情必须独立展示商品和订单子结果。平台明确无能力时显示
`UNSUPPORTED`，支持但日期/范围当前不可用时显示 `UNAVAILABLE`，本次运行错误时
显示 `FAILED`；任何一个子结果不得抹掉另一个已接受事实。当前平台能力为：

```text
supports_order_scan = true
supports_current_trade_day = false
supports_historical_trade_day = true
```

允许的 Web 操作：

- 暂停/恢复只读计划。
- 安全补跑只读扫描或日结。
- 查看运行步骤和失败原因。
- 跳转关联异常和结果。

禁止：

- 从自动化页面批量扫描 `pending` 或发布普通改价、上架、下架 COMMIT。
- 在生产 Web 中提供“手工模拟 S4 并立即下架”的旁路；`SYSTEM_EMERGENCY` 只能由
  版本化策略和二次观察驱动。
- 在 Web 请求线程中直接执行长期脚本。

### 6.6 待处理

列表字段：

- 严重度。
- 异常摘要。
- 影响对象。
- 首次/最近出现。
- 出现次数。
- 负责人。
- 当前状态。
- 建议动作。

详情按“影响—时间线—自动处理—人工处理—证据—恢复确认”显示，并区分 Review 与
Incident 状态。Incident 必须使用 S0–S4 和 `OPEN / RETRYING / WAITING_HUMAN /
ACKNOWLEDGED / AUTO_PROTECTING / RESOLVED / CLOSED`；确认不等于解决。

### 6.7 销售分析

第一版不追求复杂 BI，优先提供：

- `ORDER_OBSERVED` 与 `SCAN_ESTIMATED` 分栏或显式切换。
- 卖家实收金额、有效数量和卖家实收单价；不可得订单数不展示为 0。
- 品种 × 等级矩阵。
- 10/30/60 分钟时段曲线、16:00–18:00 高峰份额和 18:00–20:00 早期销售。
- 上架时长、销售速度、缺货时长和库存消耗。
- `ORDER_COMPLETE / ORDER_PARTIAL / SCAN_ESTIMATED_HIGH / SCAN_ESTIMATED_MEDIUM /
  SCAN_ESTIMATED_LOW / UNAVAILABLE` 质量。
- `PROVISIONAL → OBSERVED → RECONCILED → FINAL` 日结状态和 supersedes 关系；
  只有 `FINAL` 是正式终态。

当前交易日订单不可读时显示 `supports_current_trade_day=false` 的运营文案和估算质量，
不能展示 0 冒充真实结果。

### 6.8 系统维护中的执行与审计

默认列表以“一个业务批次一行”展示：

- 动作。
- 商品数。
- 成功/失败/未知数。
- 开始和结束时间。
- 来源任务。
- 当前结果。
- 是否需要处理。

详情分层：

1. 运营摘要。
2. 逐商品结果。
3. UNKNOWN/RECONCILE 时间线。
4. 证据摘要。
5. 高级诊断：operation、attempt、phase、hash、合同和原始 JSON。

原始 JSON 和大字段必须按需加载，不能在列表页面提前递归渲染。

### 6.9 平台商品

- 区分 `ONLINE_PULSE` 当前在线事实和 `FULL_MARKET_SCAN` 双页位置事实。
- 显示最近观察时间、批次完整性、映射状态、平台价格、库存和轨迹差异。
- 显示关联 Incident、写锁、Review 和任务，不在列表递归展开原始证据。

### 6.10 业务资料

- 将商品资料、库存操作、平台映射和规则配置分组，不在一个页面堆叠所有概念。
- 编辑表单按需渲染；列表中不为每条商品预生成完整隐藏表单。
- URL 只传业务筛选和记录 ID，不传运行库或本地 Excel 绝对路径。
- Excel 管理保留为管理员高级工具，并显示“适合批量维护，不适合日常操作”。

### 6.11 系统维护

默认只展示：

- 总体健康。
- 异常服务。
- Worker 新鲜度。
- 队列和 Outbox 积压。
- 数据库/备份。
- 磁盘和证据保留。

正常检查项折叠；异常项优先展开。

测试通知必须显示：

- 目标渠道。
- 当前环境。
- 不包含业务敏感数据的说明。
- 明确的确认动作。

## 7. 视觉和交互规范

### 7.1 字体

- 运营后台正文改用系统无衬线字体：
  `"Microsoft YaHei UI", "PingFang SC", "Noto Sans CJK SC", sans-serif`。
- 数字和金额使用等宽数字特性。
- 代码和 ID 仅在高级诊断中使用等宽字体。

### 7.2 色彩

- 蓝色：信息和可继续。
- 绿色：成功、健康和已确认。
- 黄色：注意、接近截止和数据可能不完整。
- 红色：阻断、S3/HIGH、S4/CRITICAL 和失败。
- 灰色：历史、取消和不适用。

- 表格支持固定关键列、列选择、紧凑模式和横向滚动提示。
- 主操作每页原则上不超过一个；危险操作与普通操作分组。

### 7.4 可访问性

- 所有表单使用真实 label。
- 键盘可完成筛选、打开详情和提交复核。
- 焦点状态清晰。
- 状态颜色满足对比度要求。
- 模态框关闭后焦点回到原触发点。
- 页面标题、heading 层级和 landmark 不重复。

## 8. 技术重构方案

### 8.1 保持现有路线

本任务继续使用当前 Python WSGI + 服务端渲染模式，保留：

- 登录和 Session。
- CSRF。
- 现有 service/repository。
- 现有 Mobile Review。
- 任务 12/13 的执行合同和结果导入。

### 8.2 拆分当前大文件

当前 `app/web.py` 约 384 KB，路由分发、表单解析、业务调用、HTML 拼接和技术诊断混在
同一文件。建议逐步拆为：

```text
app/
  web.py                         # 兼容 WSGI 入口，迁移期只委托新应用
  webapp/
    application.py               # WSGI 应用组装与路由注册
    auth.py                      # 登录、Session 和角色边界
    csrf.py                      # CSRF 生成与校验
    routes/
      dashboard.py
      platform_products.py
      sales.py
      automation.py
      work_queue.py
      tasks.py
      business_inputs.py
      system.py
    presenters/
      view_models.py             # 运营显示模型，不暴露原始 repository 行
      dashboard_presenter.py
      task_presenter.py
      incident_presenter.py
      sales_presenter.py
    templates/                   # 受控模板层，默认转义
    static/                      # 设计 token、组件和响应式资源
```

业务应用服务继续保留在 `app/services/`。`presenters/` 只负责显示语义和 ViewModel，
不得复制业务规则、直接写库或修改状态。

不要一次性重写全部 `app/web.py`。每完成一个页面，使用路由级回归证明旧写入链路和安全
边界不变。若模板层引入 Jinja 或新增静态资源构建依赖，必须更新 wheel 打包清单并执行
隔离安装测试；不能只依赖开发机源码目录。

### 8.3 View Model

新增只读显示模型，将数据库值转换为运营语义：

- `TaskListItemView`
- `TaskDetailView`
- `ReviewWorkItemView`
- `AutomationRunView`
- `IncidentView`
- `ExecutionBatchView`
- `DailySalesSummaryView`

View Model 负责：

- 中文状态。
- 下一步动作。
- 数据新鲜度。
- 影响摘要。
- 安全的技术 ID 摘要。

它不能修改业务状态，不能替代 service 层。

### 8.4 路由策略

优先保持已有主路径，减少一次性迁移：

| 当前路径 | 重写后 |
| --- | --- |
| `/dashboard` | 保留，升级为今日运营 |
| `/tasks` | 保留，增加人工/自动/系统紧急分组和独立详情 |
| `/reviews` | 保留，主入口并入“待处理” |
| `/notifications` | 保留兼容，主入口并入“待处理”或“系统维护” |
| `/execution-logs` | 保留兼容，主入口并入“系统维护”的批次摘要 |
| `/business-inputs` | 保留，主入口升级为“业务资料” |
| `/task-generator` | 保留兼容，入口移入任务中心 |
| `/system` | 保留，升级为“系统维护” |
| `/tables` | 保留为管理员高级工具 |

新增详情路径时使用稳定 ID，例如：

- `/platform-products`
- `/sales`
- `/automation`
- `/work-queue`
- `/tasks/{task_id}`
- `/reviews/{review_task_id}`
- `/automation/runs/{run_id}`
- `/incidents/{incident_id}`
- `/executions/{batch_id}`

旧 query 详情路径保留 302 或兼容渲染，直到测试和文档完成迁移。

### 8.5 页面性能门禁

- 列表默认最多渲染 25 行。
- 列表页面不渲染未选中详情。
- 原始 JSON、运行日志和大证据按需加载。
- 单个常规列表页面 DOM 节点建议不超过 2000。
- 常规页面 HTML 建议小于 500 KB。
- 不在 URL 中携带本地绝对文件路径。
- 不把 50 条执行记录的原始输出递归展开到同一页面。

## 10. 测试和验收

### 10.1 核心运营任务

- 进入系统后 3 次点击内找到今天最紧急的待办。
- 判断最近小扫描和完整扫描是否新鲜。
- 找到一个自动生成任务的来源运行。
- 完成一个无需 JSON 的复核。
- 从异常跳转到关联任务、扫描或执行结果。
- 查看一个批次中每个商品的结果。
- 查看某日某品种/等级的销售和时段分布。
- 管理员能定位原始 operation/attempt/phase，但运营人员默认看不到。

### 10.2 内容验收

- 主列表不直接显示未翻译内部枚举。
- 主流程不要求输入 JSON、hash、ID 组合键或本地路径。
- 所有状态同时说明“当前含义”和“下一步”。
- 数据为 0、未同步、不完整和读取失败四种状态明确区分。
- 测试数据与真实运营数据明确区分。

### 10.3 响应式验收

- 390 像素宽度下首屏可以看到页面标题和主要待办。
- 导航不占据连续三行内容区。
- 除明确的高级数据表外，页面不产生整页横向滚动。
- 表单按钮和字段不被截断。
- 模态框可关闭且焦点恢复。

### 10.4 安全验收

- 登录、Session、CSRF、POST logout 和安全 header 回归通过。
- 不展示 secret、raw token、完整 webhook、客户个人信息或本地绝对路径。
- 高级诊断不允许绕过 service 执行写操作。
- 测试通知和安全补跑有明确目标、环境和审计。
- 自动化页面不能发布普通写 COMMIT，也不能手工旁路触发 `SYSTEM_EMERGENCY`。
- S4 紧急保护必须展示策略版本、两次观察、禁止条件、明确任务、执行结果和恢复状态。

### 10.5 性能验收

- 使用当前 146 条任务、53 条复核和现有执行历史做大数据量回归。
- 任务和复核详情不再附带完整列表。
- 执行列表不再递归渲染原始输出。
- 分页、筛选和详情页面的 HTML/DOM 体积符合第 8.5 节门禁。
