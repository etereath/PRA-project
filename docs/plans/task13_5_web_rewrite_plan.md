## 1. 本轮决策

13.5-7 不再以旧 Web 的页面清单或历史计划档案为产品设计起点。当前项目尚未正式投入
运营，没有旧路由、旧会话或双 Web 的生产兼容义务。新 Web 以实际使用为主，由运营路径
反向约束页面、Application Service、Read Model 和施工顺序。

权威顺序固定为：

1. 用户确认的实际运营流程；
2. 当前四入口静态样板和本计划冻结的业务定义；
3. 已验证的领域事实、安全门禁和唯一执行链；
4. 当前施工计划；
5. 旧 Web、历史页面清单和已被取代的计划文字。

UI 可以改变历史信息架构，但不能推翻以下安全事实：数据库页只读、普通任务不能因
`PENDING` 自动执行、平台写操作必须经过 Task/授权/Queue/Worker/Importer/回读、
`UNKNOWN` 只能进入唯一 RECONCILE、Agent 不直连 Web/数据库/Queue/平台、
`SYSTEM_EMERGENCY` 继续遵守 13.5-6 的全部门禁。

## 2. 四个一级入口

桌面与手机只保留同一组一级入口：

1. **今日**：当日经营摘要、必须处理、业务时间轴和健康摘要；
2. **数据库**：业务事实、项目运行事实、销售分析、字段说明和质量；
3. **业务管理**：创建任务、授权执行、人工复核、自动化方案和真实库存业务；
4. **系统**：当前组件状态、通知通路、数据维护、权限边界和高级诊断。

旧八入口不机械保留为二级页面：

| 旧入口 | 最终处理 |
| --- | --- |
| 今日运营 | 成为“今日” |
| 平台商品 | 数据并入数据库商品、价格和映射；删除独立页 |
| 销售分析 | 保留为数据库二级入口，为未来 Agent 分析预留稳定位置 |
| 自动化 | 方案管理并入业务管理；Run 历史进入数据库 |
| 待处理 | 摘要进入今日；完整处置进入业务管理人工复核 |
| 任务中心 | 当前任务进入业务管理；历史进入数据库；删除旧页 |
| 业务资料 | 写入表单按业务归入业务管理；结果进入数据库 |
| 系统维护 | 成为“系统” |

旧页面若只重复事实、服务兼容旧 Web 或主要展示开发者信息，必须连同专属 Route、
Presenter、模板和重复测试一起删除。只有 `/health`、登录/退出、Mobile Review 和稳定详情
URL 作为必要外部协议保留。

## 3. 页面业务合同

### 3.1 今日

今日只回答“卖了多少、还剩多少、必须处理什么、系统是否影响业务”。页面顺序为：

- PRA 交易日、OPEN/CLOSED/结算状态、最近更新时间和数据质量；
- 当前必须处理的 Review、Incident、映射、库存和系统影响摘要；
- 今日销量、成交金额、成交均价、数据库真实库存和库存偏低商品数；
- 品种/等级销售与库存表格；
- 扫描、订单读取、18:00、20:00、结算、任务和执行时间轴；
- Automation、Worker、Importer、通知的业务影响摘要。

今日不展示完整历史、技术日志或复杂配置。“数据完整度百分比”没有权威算法，固定删除；
缺失、过期和失败不能显示成 0。销量必须标明订单事实或扫描估算，二者不能相加。

### 3.2 数据库

数据库是运营只读数据中心，不是 SQLite 管理器。分页固定为：

- 业务数据；
- 项目运行数据；
- 销售分析；
- 字段说明；
- 质量与新鲜度。

业务数据至少包括销售与订单、商品与真实库存、平台价格、交易日结算、品种销售结构、
库存调整流水、商品映射和历史经营快照。项目运行数据至少包括任务、复核、Automation、
Incident、执行和通知。

一次只展示一个数据集，默认 25 条，使用服务端分页和窄查询；不得先全量加载再浏览器
分页。默认不显示数据库主键、Hash、Queue 路径和原始 JSON，必要技术证据进入系统高级
诊断。

销售分析当前只展示可由既有事实确定计算的销量、金额、均价、分时结构、库存消耗、
订单/估算差异和质量影响。未来 Agent 预测、趋势解释与经营建议继续使用同一入口；未接入
前不显示假建议、空卡片或“生成预测”按钮。

### 3.3 业务管理

业务管理只保留三个分页：创建任务、人工复核、自动化方案。人工库存调整是创建任务
区域中的独立弹窗，不再占据分页。

#### 创建任务

弹窗按品种、等级、平台三个维度多选，只展开真实存在且映射唯一的商品。任务类型为：

- 调整价格到；
- 加/降价，负数表示降价；
- 下架商品；
- 上架商品，输入上架价格和平台目标库存。

“加/降价”由后端根据最新可信价格计算逐商品绝对目标值，最终仍形成既有
`UPDATE_PRICE`。映射缺失、价格过期、低于基础成本、库存不足、冲突任务、`UNKNOWN`
或未完成 RECONCILE 均必须阻止创建或提交执行。

任务创建与真实平台执行授权是两个后台阶段，但 UI 可以连续完成：

```text
选择范围与动作
→ 展开具体商品并预览
→ 保存正式 Task
→ 重新校验当前事实
→ 运营者确认提交执行
→ Queue → Worker → Importer → 独立回读
```

创建 Task 不等于平台写入。普通 `PENDING` 不得被无人值守扫描并自动执行。“提交执行”
使用独立权限并记录授权人和授权时间。

#### 人工复核

复用既有 Review、Incident、Outbox 和原子处置服务。运营页使用中文说明发生了什么、影响
什么、建议动作和等待时间。业务选择固定使用结构化动作，例如“改价到指定值、立即下架、
我来处理”；验证码等人工动作必须有“处理完毕”反馈。人工产生的改价/下架和超时产生的
紧急下架必须优先于普通任务。

#### 自动化方案

只管理冻结类型的方案，不开放脚本、任意 Job 或 Cron 编辑器。允许在安全范围内启停、
修改频率/时间、查看下一次运行和最近结果，并对允许的 READ_ONLY 作业补跑。至少覆盖：

- 每 10 分钟小扫描；
- 每小时完整扫描；
- 订单读取；
- 交易日边界扫描和 20:00 日结；
- 结算补跑、复核超时维护、每日任务生成；
- 数据库真实库存预警。

库存预警支持默认阈值和特定商品覆盖；只在越过阈值时创建提醒，持续偏低遵守既有重复
提醒策略，恢复后解除。预警本身不直接下架商品。

### 3.4 系统

系统“运行状态”只显示组件当前状态、状态依据、业务影响和恢复动作，不复制数据库中的
Run、Task、Queue 文件和历史通知。详细历史统一进入数据库项目运行数据。

系统至少覆盖 Web、Automation、Worker、Queue、Importer、Outbox/飞书、Runtime DB 和
备份。Worker 恢复必须完整复用 `AGENTS.md` 的生命周期流程，不能只显示等待，也不能在有
活动请求时重复启动。

系统还提供受保护的飞书测试、显式数据库维护、备份/回读状态和高级诊断。普通 GET 永不
调用 `init_schema()`、迁移或修复；数据库问题只报告，维护必须先备份并回读。

## 4. 两类库存

### 4.1 数据库真实库存

数据库库存代表农场当前还有多少花可以卖，是销售扣减、库存预警、销售计划和上架安全
校验的权威余额。人工弹窗只输入：商品、有符号调整值、来源和原因；输入框下方提示调整前、
本次变动和调整后库存。默认来源与原因为“新花入库”。

真实库存需要按权威销售事实自动调整：

```text
最新有效销量事实
→ 与已应用销量比较
→ 只应用差额
→ 写入不可变库存流水
→ 更新余额
→ 重新判断预警
```

完整订单事实优先于合格扫描估算，替换时只应用差额；重复观察不重复扣减；不完整、失败、
日期错位不改库存；已确认取消恢复对应数量；超过现有库存时进入人工复核，不允许负库存。

### 4.2 平台库存

平台库存只是买家在特定平台最多还能购买的数量或上架时设置的可购上限，不代表农场真实
库存。当前单平台的目标平台库存不得超过数据库真实库存。人工入库只改真实库存；若需要
改变平台库存，必须创建正式平台任务。未来多平台库存分配另开合同，不在 13.5-7 实现。

## 6. 唯一控制面职责

| 调用方 | 正式职责 |
| --- | --- |
| Web | 人工查看、创建、复核、配置和明确执行授权 |
| Automation | 定时 READ_ONLY、结算、维护和已授权的专用紧急策略 |
| Agent Gateway | 未来结构化 Query/AgentIntent；不抓 Web、不直连数据库或平台 |
| Queue/Worker/Importer | 唯一平台执行、结果导入和归档链 |
| CLI | 开发、测试、Mock、诊断、备份、恢复和应急工具 |

日常业务 CLI 必须迁到上述正式归宿；测试 CLI 继续保留且可以直接调用相同 Application
Service。不能为 Web 或 Agent 新建第二套状态机、任务表、平台执行器或库存余额。

## 7. 安全与权限

最低能力固定为：查看今日、查看数据库、管理业务、处理复核、提交执行、系统管理。当前
管理员可以拥有全部能力，但“已登录”不能等同于“系统管理员”。权限判断集中实现，导航
显示和后端 Route 使用同一来源。

开发环境必须显式设置 `PRA_ENV=development` 并使用非 Secure Cookie；生产必须 HTTPS
和 Secure Cookie。协议、环境与 Cookie 冲突时拒绝启动并给出中文原因。Runtime DB、工作
簿和 Queue 路径由 Composition Root 在启动时固定，URL、Session 和表单不能切换。

所有写操作要求 CSRF、权限复核、幂等键、服务端校验、版本冲突检查、事务、失败回滚、
PRG 和中文结果。提交执行、紧急开关、恢复备份、迁移/修复和关键服务恢复需要二次确认。

## 8. 通知、详情和跨页

四入口共用通知铃铛，角标表示未解决事项而不是未读消息。查看通知不改变 Review/Incident。
通知按业务类型跳到业务管理、数据库或系统，完整通知历史留在数据库。

同一实体只有一个正式详情页：商品/销售/结算/运行事实属于数据库，当前任务/复核/方案属于
业务管理，系统故障属于系统。完成任务仍使用同一任务详情，只是进入只读状态。跳转保留
PRA 交易日、品种、等级、平台、商品、状态和来源页，不携带本地路径或凭证。

飞书是通知与反馈通道，不建立第二套业务状态。Mobile Review 必须处理有效、失效、过期、
已完成和重复点击；“处理完毕”必须回写正式结果，发送成功或阅读消息都不代表问题解决。

## 9. 不兼容切换和 CLI 迁移

新 Web 完成验收后一次性替代 `app/web.py` 的旧页面架构，不保留旧路由兼容层、不运行双
Web。`/health` 和 Mobile Review 外部协议保持稳定。Web 启停与 Automation、Queue Service、
Worker 解耦；Web 重启不得影响后台执行。

迁移前逐项建立 CLI → Web/Automation/Queue/保留诊断矩阵，特别核对
`BusinessRuleRunner` 与 `generate_runtime_tasks_from_sources` 两条历史链。包装、冷库 ERP、
未进入当前范围的 capacity/platform_sync evaluator 不得用含糊的“每日任务生成”宣称完成
迁移；必须明确保留诊断、延期或删除。

## 11. 验收原则

- 四入口使用真实 Read Model，不用演示值冒充业务事实；
- 桌面、手机和飞书直达形成完整闭环；
- OPEN/CLOSED、质量、订单/估算、真实/平台库存语义正确；
- 普通 GET 前后 Runtime DB、工作簿和 Queue 零变化；
- 所有列表服务端分页，空、过期、不完整、失败和权限不足可辨；
- 创建任务不写平台，提交执行前重新校验并明确授权；
- Web 重启不影响 Automation、Queue、Worker、Importer；
- 真实平台 COMMIT 仅在单独批次授权后进行；
- 删除旧 Web 页面、兼容层和重复控制面；
- 文档、样板、实现、测试和真实验收结论一致。
