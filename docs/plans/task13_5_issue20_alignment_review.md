## 1. 权威层级

任务 13.5 后续开发按以下顺序处理冲突：

1. Issue #20 冻结的业务目标、双时间轴、事实口径、异常等级、紧急保护流程、阶段划分和任务 14 边界。
2. 当前代码、数据库约束、自动化测试和真实运行证据所揭示的工程事实。
3. 本地 Codex 计划中的模块拆分、兼容策略、页面性能预算、ViewModel、可访问性和回归方法。
4. 任务 12/13 的历史计划与交付文档，仅作为已完成能力和兼容约束的证据。

本地实现可以把 Issue #20 的目标细化为接口、表、路由、迁移和测试，但不得修改其已经冻结的业务语义。若实机页面能力与 Issue 假设不一致，应记录能力缺口并降级，不得伪造数据。

## 2. 总体评价

两份计划的方向一致：都要求把零散脚本整理为独立自动化服务，把扫描、订单观察、销售日结、异常处置、任务来源和 Web 运维界面组成单平台闭环，并继续复用任务 12/13 已验收的 v5 写动作、Importer、写锁和唯一 RECONCILE。

Issue #20 的优势是业务闭环更完整，尤其补齐了：

- 平台交易日与卖家作业日的双时间轴。
- 当前订单页不可可靠读取时的能力声明和降级规则。
- 不可变观察批次、无伪造订单 ID 的多重集建模。
- `ORDER_OBSERVED` 与 `SCAN_ESTIMATED` 两类销售事实。
- S0–S4 异常等级、重复提醒和 S4 紧急下架保护。
- 统一 UI 通道优先级、自动化运行账本和任务来源合同。
- 任务 13.5-0 至 13.5-10 的完整阶段，以及收窄后的任务 14。

本地计划的优势是直接基于当前项目和浏览器实测，能够给出：

- 当前 Web 的真实页面规模、表格长度、移动端布局和运营可读性问题。
- `app/web.py` 巨型模块的实际拆分边界。
- 服务端渲染、兼容路由、ViewModel、分页和按需展开的具体做法。
- 可量化的页面性能、可访问性、回归测试和迁移门禁。
- 对现有 v5、Importer、SQLite 和测试套件的低风险复用策略。

因此不是二选一，而是“Issue 定义做什么和为什么，本地计划定义在这个仓库里怎样安全完成”。

## 3. 差异与裁决

| 小扫描 | `ONLINE_PULSE`，每 10 分钟，仅上架中 | `ONLINE_DELTA` | 统一改为 `ONLINE_PULSE` |

## 4. 本地浏览器实测对计划的补充

Issue #20 的 Web 信息架构是最终一级导航。以下本地实测结果作为页面重写的工程输入：

- 任务列表当前有 146 条记录，单页 50 条、12 列；桌面表格约 1335 px，移动端约
  1239 px，桌面页面高 5330 px。
- Review 页面有 53 条记录，直接暴露内部枚举、复合键和结果 JSON 输入。
- 通知页面有 41 条记录，未配置或取消项容易被运营人员理解为失败。
- 执行日志页桌面高 31704 px；32 条顶层日志递归形成 32 个嵌套表和 684 个后代行。
- 自动化页面仍提示通过 CLI 应用，未形成真正的运营控制面。
- 业务资料集中六个标签页，长 URL、本地路径和预渲染编辑表单造成阅读噪声。
- 390 px 移动视口下导航约占 169 px 高，首屏有效信息不足。
- 当前 `app/web.py` 约 383965 字节，`app/web_styles.py` 约 15034 字节；继续叠加路由会放大回归面。

这些发现不会改变 Issue 的八个一级入口，但决定了本地实现必须采用服务端分页、摘要优先、原始数据按需展开、响应式导航和渐进模块拆分。

精确时间、main SHA、Runtime DB 脱敏快照、浏览器/视口/角色、完整路由和 DOM 摘要
hash 见 [Web 现状独立审计快照](task13_5_web_current_state_audit_20260729.md)。上述数字
只描述该快照，不是长期常量。

## 5. 合并后的 Web 实施原则

一级导航严格采用 Issue #20：

1. 今日运营
2. 平台商品
3. 销售分析
4. 自动化
5. 待处理
6. 任务中心
7. 业务资料
8. 系统维护

本地实施细节：

- “待处理”承接原异常中心、Review、登录失效、映射缺失、页面漂移、UNKNOWN、通知失败和低置信销售估算。
- “任务中心”按人工、自动、系统紧急和全部任务分组；扫描运行只在自动化页显示，不伪装为普通任务。
- “系统维护”承接执行审计、原始日志、合同版本、证据、Worker、队列、Outbox、备份和高级诊断。
- 页面路由先保持兼容并引入 presenter/ViewModel，随后把新路由迁移到 `app/webapp/routes/`，避免一次性重写 38 万字节模块。
- 详情页默认回答“发生了什么、影响什么、系统做了什么、需要我做什么”；原始 JSON、phase、hash 和本地路径默认折叠。
- 列表必须服务端分页；大日志和证据不得随首屏同步展开。

## 6. 已冻结的业务规则

以下内容不再作为本地开放问题：

- 时区为 `Asia/Shanghai`。
- 平台交易日以 18:00 为边界；卖家作业日以 20:00 为边界。
- `NORMAL_SALES` 为 20:00 至次日 16:00，`PEAK_SALES` 为 16:00 至 18:00，`DELIVERY_OVERLAP` 为 18:00 至 20:00。
- `SETTLEMENT` 是 20:00 后的后台作业，不是排他的全局阶段。
- 边界测试至少覆盖 17:59、18:00、19:59 和 20:00。
- 跨边界扫描按每条观察的 `observed_at` 归属交易日。
- `FULL_MARKET_SCAN` 保持 `LISTING_STATUS_SCAN / ORDER_SCAN` 通用父子合同；能力和
  `UNSUPPORTED / UNAVAILABLE / FAILED` 由 Adapter 表达。
- 当前订单页不可可靠读取时必须公开显示数据能力和质量，不得推断为实时完整订单。
- 指纹只是订单行候选分组和完整性校验；真实重复行以
  `occurrence_no / occurrence_count` 保留，跨批次按多重集合比较。
- `fact_source / quality_level / summary_status` 独立保存；质量使用六级矩阵。
- 20:00 日结先生成 `PROVISIONAL`，后续按
  `OBSERVED → RECONCILED → FINAL` 推进；只有 FINAL 是正式终态，迟到修正使用
  supersedes 新版本。
- 库存估算区间必须保存已知调整来源、映射版本、资格原因、置信度和支撑观察；不合格
  区间不得记为销量。
- S4 不在 13.5-1 写最终方案，但仍必须在 13.5-6 完成；人工 Incident 闭环和真实
  支撑数据先通过评审，再冻结策略、迁移结构并实现 `SYSTEM_EMERGENCY`。
- 只有满足版本化 S4 策略、二次观察、人工介入检查和全部禁止条件的
  `SYSTEM_EMERGENCY` 才能自动下架；不得自动重新上架。

## 7. 对任务 14 的新边界

任务 13.5 必须完成控制服务、扫描与订单观察、销售估算与日结、异常分级、紧急保护、脚本收口、任务来源对齐和 Web 产品化。

任务 14 不再负责补做这些基础控制面。它只负责：

- 多品种、多动作和异常恢复的综合验收。
- 普通写动作的正式授权与策略验收。
- `SYSTEM_EMERGENCY` 策略的安全验收。
- 观察版本冻结和交付判定。

任务 15、16、17 分别承接 24 小时/7 天观察、第二平台或预测影子运行，以及运维看板、备份、保留策略、Runbook 和项目收口。

## 8. 实施判断

Issue #20 可以直接作为任务 13.5 的父实施计划，但不能一次性开发。推荐按照 13.5-0
至 13.5-10 顺序推进，每阶段先冻结合同和验收场景，再修改数据库与代码。当前
13.5-0 已获准；13.5-1 只允许先做合同和 Schema 设计，六级质量矩阵和日结状态机评审
通过后才允许提交 v14 迁移。

Web 端必须后于双时间轴、观察批次、任务来源和异常合同冻结，否则页面会再次把临时字段固化成运营概念。与此同时，Web 的架构拆分可以先在不改变业务行为的前提下建立兼容壳、ViewModel 和测试基线，为 13.5-9 的 UI 重写降低风险。
