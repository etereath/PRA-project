# ShadowBot 任务12—13复用路径与失败复盘

- 复盘日期：2026-07-28
- 适用范围：任务13.5、任务14及后续真实平台任务、第二平台探索、现有 ShadowBot 链路维护
- 性质：工程执行手册和防复发门禁，不替代任务12、任务13最终交接报告

## 1. 核心结论

任务12和任务13已经证明，后续真实平台任务最有效的开发方式不是重新设计
Worker，而是把新能力接到已验收链路的明确扩展点：

```text
冻结最后成功基线
→ 列出本任务相对基线的最小差异
→ 只读探索页面结构
→ 冻结合同、状态和副作用边界
→ 先生成完整执行计划，不产生副作用
→ 接入一次投递的完整队列
→ 在首个写动作前完成全批次门禁
→ 按计划严格串行执行，每项独立回读
→ Importer 原子投影，UNKNOWN 只进入唯一 RECONCILE
→ 保存脱敏证据并运行自动复算
```

任务12已经出现、任务13又重复出现的问题，不应再只作为历史说明。它们需要成为
后续任务开始前的强制检查项：

1. 不得删除或重写已成功的动作链路来实现相邻能力。
2. 不得在同一轮同时改合同、页面读取、点击动作、状态机和性能路径。
3. 不得用点击失败、弹窗未出现或重复滚动来探测布局。
4. 不得为 v5、第二平台或新动作复制一套批次终态、发布边界或 UNKNOWN 语义。
5. 不得只在 proposal 阶段检查任务和 Review；持久化前必须在同一写事务内复核。
6. 不得把平台事实、页面位置、人工处置和写操作副作用压成一个状态字段。
7. 不得把“测试通过”“影刀实机成功”和“文档已更新”互相替代。

## 2. 后续任务应复用的标准实施路径

### 2.1 建立黄金基线卡

开始修改前必须记录：

| 项目 | 必须记录的内容 |
| --- | --- |
| 代码 | 分支、commit SHA、部署文件 SHA-256 |
| 实机 | 最后成功 batch/run/attempt ID |
| 输入 | 合同版本、任务 ID、SKU、旧值和目标值 |
| 输出 | result、phase、receipt、ACK、数据库回读 |
| 动作 | 已验证的定位、点击、确认和回读函数 |
| 允许修改 | 本任务真正新增的合同字段、页面和状态 |
| 禁止修改 | 已验收动作链路、UNKNOWN/RECONCILE 和发布边界 |

任务12的黄金动作基线是
`BATCH-T12-OPTIMIZED-COMMIT-20260721-02`。任务13的后续维护应以
[任务13最终交接报告](reports/task13_final_handoff_20260727.md)所列的正常
上下架、严格串行 UNKNOWN 和两类 RECONCILE 证据为基线。不能只记住“以前成功
过”，必须能定位到代码和证据。

### 2.2 先写差异清单，再写代码

差异清单至少回答：

1. 新任务新增了哪种业务动作或页面？
2. 哪些已有函数可以原样调用？
3. 哪些状态、锁、账本和结果字段可以原样复用？
4. 新副作用发生在哪个最终确认边界？
5. 哪些失败必须是 `NOT_APPLIED`，哪些必须是
   `PARTIALLY_APPLIED`，哪些必须是 `NEEDS_RECONCILIATION`？
6. 新代码是否真的需要新的合同版本或表结构？

如果答案只是“把同一种动作扩展到多个商品、另一个页面或正式任务输入”，默认
采用最小扩展，不得重建 READ_ONLY、预览、队列、Importer 或 RECONCILE。

复用裁决必须按以下顺序执行，不能直接从第 4 步开始：

1. **原样复用**：直接调用已验收入口，保持合同、控制流、状态和错误语义不变。
2. **参数化复用**：只增加选择器、字段解析器、页面类型或无副作用配置参数。
3. **抽取公共能力**：从最后成功链路中提取通用助手，并让旧调用方和新调用方共同
   使用；旧成功基线必须继续通过。
4. **新增实现**：仅在前三步均有可复现的不兼容证据时允许，且必须记录替代方案、
   风险、测试矩阵和实机验收范围。

“新页面”“新 Adapter”“代码更短”“当前只有单页数据”都不是新增平行实现的充分
理由。平台专属部分是选择器、页面入口、字段步长和解析规则；聚焦、加载、滚动、尾部
验证、回顶、进度证明、超时和失败关闭属于执行体系，应优先共享。

对于同一小程序宿主中的列表，任务 12 的已验证语义默认是强制基线：

```text
定位并聚焦首项
→ END
→ 等待数据加载
→ 验证明确定义的尾部标记
→ HOME
→ 验证首项恢复
→ 读取完整元素树
```

若某页面不能沿用该语义，开发者必须先保存只读失败证据并完成评审；不得先写另一套
滚动函数，再用单页测试或未进入滚动分支的实机样本宣称完成。

每个子任务必须在合同或实施报告中填写以下复用矩阵；空白项或笼统填写“已复用”不
满足门禁：

| 职责 | 既有入口与成功证据 | 裁决 | 本次最小差异 | 不兼容证据/评审 | 必须回归 |
| --- | --- | --- | --- | --- | --- |
| 示例：列表物化 | 任务 12 聚焦/END/尾部/HOME 基线及实机 Run | 抽取公共能力 | 订单选择器、首项和解析器 | 无；不得新增平行实现 | 任务 12 基线 + 订单多页实机 |

`裁决` 只允许填写“原样复用 / 参数化复用 / 抽取公共能力 / 确需新增”。选择“确需
新增”时，不兼容证据和评审结论不得为空；选择其他三项时，旧调用方回归不得为空。

### 2.3 探索、计划和写操作分三层

建议固定为三层：

1. **只读探索层**：确认页面、列表结束标记、索引步长、字段偏移、确认弹窗和
   可点击边界。
2. **执行计划层**：完整扫描后完成目标唯一匹配、门禁、页面顺序和滚动轨迹；
   输出计划但不点击最终确认。
3. **正式写入层**：复用已验收动作函数，严格按计划执行；每项完成后立即独立
   回读，不在执行中重新发明定位策略。

这三层可以共享读取函数，但不能混淆权限。只读探索通过不等于正式写入已授权，
计划正确也不能证明平台副作用已经完成。

### 2.4 用同一套控制平面承载新动作

后续动作应继续复用：

- 明确选择的 `task_id`；
- SKU 到页面身份的唯一映射；
- proposal 和统一 action gate；
- `BEGIN IMMEDIATE` 内的任务、Review 和写锁复核；
- 公共 batch registry；
- operation、attempt、phase 和 item 账本；
- 文件队列原子发布、Worker 租约、Watchdog、Importer 和归档；
- UNKNOWN 后唯一只读 RECONCILE；
- 脱敏证据清单与 CI 复算。

新动作只应增加动作特有的目标字段、页面扫描和最终确认函数。不要复制公共控制
平面后再局部修改。

## 3. 任务12已经出现、任务13再次出现的失败

### 3.1 未把成功基线当作不可随意改写的资产

**任务12：** 单商品 COMMIT 已经通过，却一度重新引入 fresh READ、
FILL_PREVIEW 和新的 READ_ONLY 主路径，把“扩展成队列”做成重写整条链路。

**任务13：** 已有严格串行和页面顺序经验，早期多商品上架仍采用“先修改全部
资料，再统一点击上架”。滚动后按钮离开视口，导致后续商品无法按计划点击。

**共同根因：** 只复用了代码片段，没有冻结成功链路的控制流和隐含页面状态。

**强制门禁：**

- 新任务必须提交基线卡和函数级差异。
- 若修改已验收动作函数，必须先解释为何不能通过调用或包装扩展。
- 对“删除旧链路并重写”的变更默认拒绝，除非旧链路有可复现缺陷和迁移计划。

### 3.2 把滚动当成失败补救，而不是执行计划的一部分

**任务12：** 第 4 行及以后商品不可见时，曾考虑“未出现弹窗再滚动”；该方案
会把误点击变成布局探测。

**任务13：** 第 5 行上架按钮不可点击、多商品资料先统一保存后按钮滚出屏幕，
再次暴露了同一问题。

**共同根因：** 页面行号、当前视口和下一动作没有在首次完整扫描后统一规划。

**已验证做法：**

```text
完整扫描
→ 唯一匹配所有目标
→ 按当前页面行号排序
→ 计算每项操作轨迹
→ 从上到下完成单项全部动作和回读
→ 再进入下一项
```

所有点击前先验证目标身份和元素边界。点击失败只能产生明确失败或 UNKNOWN，
不能自动滚动后盲目重试。

### 3.3 重复读取、重复初始化和重复重启造成无意义耗时

**任务12：** 每项重复登录、导航、全页读取；完整 READ_ONLY 保留“三次相同
指纹”；每轮影刀都重启。

**任务13：** 独立 `SYNC_STATUS` 一度被当成每个上架任务的外部前置；扫描中
先读第一行名称和等级再按 `END`；`END/HOME` 前后存在重复等待和扫描。

**共同根因：** 没有区分批次固定成本、逐项边际成本和真正提供安全价值的门禁。

**已验证做法：**

- 批次只完成一次登录检查、刷新、完整扫描和执行计划生成。
- 页面需要加载末尾商品时使用“聚焦列表 → 等待 0.1 秒 → `END` →
  等待 0.8 秒 → `HOME` → 全面扫描”。
- 逐项循环只保留身份确认、动作、最终确认和独立回读。
- Worker 新鲜且队列空闲时长期复用，不因普通任务切换而重启。
- 性能报告同时记录冷态、暖态、扫描次数、滚动次数和逐阶段耗时。

性能优化不能删除唯一匹配、旧值门禁、独立回读、phase 或写锁。

### 3.4 身份来源和页面身份没有一次冻结

**任务12：** 正式 SKU、开发临时 SKU、静态 JSON、状态表旧 SKU 和库存主数据
曾同时充当身份来源。

**任务13：** `艾莎` 与 `艾莎(10枝)` 曾被混淆；上架任务又依赖扫描所得价格和
库存，暴露了“任务身份、页面身份和最新观察”没有清晰分层的问题。

**共同根因：** 把内部 SKU、页面可读字段和运行时观察当成可互换事实。

**强制规则：**

- 任务和写锁使用规范 `internal_sku`。
- 商品主数据是 SKU 到页面身份的正式映射来源。
- 当前平台页面以可结构化读取的商品名称、等级及必要规格唯一匹配。
- 页面行号只属于本次扫描，不进入任务合同或长期身份。
- 如果同名同等级不足以区分规格，必须扩展稳定规格字段；不得退回视觉猜测、
  固定排序或模糊文本匹配。

### 3.5 已有的发布前复核在新合同中被不完整移植

**任务12：** v4 已经有任务在发布前变化时拒绝 COMMIT 的保护。

**任务13：** v5 初版 proposal→persist 只复核任务状态、动作和 SKU，没有覆盖
平台、目标状态、价格、库存和过期时间；Review 也曾只在 proposal 阶段检查。

**共同根因：** 复制了门禁概念，但没有复用完整安全属性和事务边界。

**最终规则：**

```text
生成 proposal
→ 用户或调度器选择是否发布
→ BEGIN IMMEDIATE
→ 重新读取当前任务、Review 和写锁
→ 规范化并重新计算完整执行载荷哈希
→ 验证任务仍未过期
→ 全部一致后才写入 batch/operation/attempt/lock
→ COMMIT
```

载荷哈希必须覆盖平台、任务、SKU、动作、目标状态、目标价格、目标库存、任务
过期时间和页面身份。新增动作时应扩展统一哈希输入，不能只增加新的零散比较。

### 3.6 同一业务语义在多个模块各写一遍

**任务12：** 已经建立共享的 v4 结果计数和批次终态推导。

**任务13：** v5 初版在合同、Worker、Worker 失败恢复和 pipeline 批次重算中
存在多套相似算法，导致 `NOT_APPLIED + NOT_ATTEMPTED` 以及全
`NOT_ATTEMPTED` 被错误算成 `PARTIAL`。

**共同根因：** 新合同沿用了字段名称，却没有沿用“单一语义函数”的工程原则。

**最终规则：**

- 结果计数与批次终态只能由
  `app/shadowbot_contract_primitives.py` 的共享函数推导。
- Worker、Importer、Watchdog/恢复、RECONCILE、报告和 Web 不得自行重写
  状态优先级。
- 必须固定组合矩阵：

| 逐项组合 | 批次状态 |
| --- | --- |
| 全部 `VERIFIED/ALREADY_APPLIED` | `VERIFIED` |
| 全部 `NOT_ATTEMPTED` | `FAILED` |
| `NOT_APPLIED + NOT_ATTEMPTED` | `FAILED` |
| `VERIFIED + NOT_ATTEMPTED` | `PARTIAL` |
| 任一 `NEEDS_RECONCILIATION` | `UNKNOWN` |
| 无 UNKNOWN，但任一 `PARTIALLY_APPLIED` | `PARTIAL` |

### 3.7 发布失败边界和逐项账本不完整

**任务12：** 文件队列发布边界已经区分“确定未发布”和“可能已发布”，并要求
UNKNOWN 后只读对账。

**任务13：** v5 初版在 runner 启动失败时没有完整终结所有 item、attempt、
operation 和 lock；若发布状态不确定，也可能缺少完整 UNKNOWN 投影。

**共同根因：** 只处理了批次表状态，没有把每个目标视为必须闭合的独立账本。

**强制规则：**

- 确定未发布：所有项 `NOT_ATTEMPTED`，attempt/operation 终结，锁释放，
  task 恢复为可重试状态。
- 可能已发布：所有受影响项进入 `NEEDS_RECONCILIATION`，attempt 为
  `START_UNKNOWN`，锁保持 `UNKNOWN`。
- 任一发布异常后必须满足逐项计数恒等式；不能只有 batch 状态。

### 3.8 只回传目标项或只验证最终状态，丢失了完整事实

**任务12：** 早期 COMMIT 只回传改价商品，后来改为回传当前页面完整商品状态。

**任务13：** 早期失败后没有统一扫描并投影最终页面信息；SET_ONLINE 若只确认
商品在线，也不足以证明价格和库存全部符合目标。

**共同根因：** 把“动作结果”误当成“页面事实快照”，或只验证复合操作的一部分。

**强制规则：**

- 动作结果、完整页面快照和数据库投影分开建模。
- 复合写操作必须逐维回读：上线事实、价格和库存缺一不可。
- 失败后扫描只有在页面范围完整、结束标记可信时才能投影平台事实。
- 写操作改变上下架状态后，旧 `listing_location` 快照失效；必须由后续完整两页
  `SYNC_STATUS` 重新证明。

### 3.9 状态概念被压成一个字段

**任务12：** 已经区分 operation UNKNOWN 与平台价格事实，但在扩展到上下架时
仍容易把“需要人工处理”当成平台状态。

**任务13：** `online/offline/manual_review`、`not_online/offline`、
`manual_review/UNKNOWN` 曾反复混用，直到冻结四维模型。

**最终四维模型：**

| 维度 | 回答的问题 | 示例 |
| --- | --- | --- |
| `online_status` | 平台是否可售 | `online/offline` |
| `listing_location` | 两页完整扫描观察到哪里 | `online_only/waiting_only/both/neither/ambiguous` |
| `automation_disposition` | 自动化是否可继续 | `actionable/manual_review`，由事实和锁派生 |
| operation/lock | 某次写操作副作用是否确定 | `VERIFIED/PARTIALLY_APPLIED/NEEDS_RECONCILIATION` |

以后新增状态前必须先说明它属于哪个维度。平台事实不能被 Review 状态覆盖，
UNKNOWN 写锁也不能被普通人工通知替代。

### 3.10 文档、证据和 PR 描述滞后于代码

**任务12：** 三轮 READ_ONLY 的 JSON、Markdown、run ID 和
`read_batch_id` 曾未完整进入交接；早期报告堆叠代码和 JSON，不够人工可读。

**任务13：** PR 描述先后出现旧测试数量、旧 Head SHA、实机证据范围不清和
任务14边界遗漏；审查后又发现门禁、发布失败和批次状态组合没有对应回归说明。

**共同根因：** 把文档当成开发完成后的手工摘要，而不是由代码、证据和 CI
共同约束的交付物。

**强制规则：**

- PR 描述记录当前 Head SHA、精确测试数量、CI 结论和实机/自动化证据边界。
- 人工报告先回答“是否成功、处理什么、逐项结果、错误、数据库是否一致”。
- 原始 JSON、phase、receipt、ACK 和哈希放证据包，不复制到正文冒充结论。
- 文档中的测试数量变化后必须同步更新，不能保留审查前数字。
- 历史计划保留追溯价值，但不得覆盖当前状态和最终合同。

### 3.11 特殊页面状态被过早判定为选择器漂移

**任务13.5-0：** 部署 hash 对齐后的前两次 `READ_ONLY` 在商品管理入口和“上架中”
标签处安全失败。用户确认小程序当时停留在尚未纳入影刀导航图的特殊页面，恢复正常
页面后，同一代码和选择器立即完成两页扫描并得到 `VERIFIED`。

**共同风险：** 单次“未找到元素”同时可能来自页面状态、加载时序、窗口上下文或真实
选择器漂移；若未建立对照就直接修改选择器，会把正常资产改坏。

**强制规则：**

- 先保留失败 result/phase/ACK，确认 `side_effect_state=NOT_STARTED`。
- 只读核对当前页面、窗口标题、登录状态和是否处于已支持导航图。
- 恢复到已知页面后，用相同部署和新 Run ID 重试一次；不得覆盖失败证据。
- 只有已知页面上的可重复失败和页面结构证据同时成立，才定性为选择器漂移并进入重新
  捕获流程。
- 失败快照不得覆盖随后通过完整性门禁的可信投影。

## 5. 可复用测试策略

后续修改分四层验证，避免“每次都跑实机”和“只跑单元测试”两个极端：

| 变更 | 最低验证 |
| --- | --- |
| 纯文档和链接 | UTF-8 回读、Markdown 链接和路径检查 |
| 纯合同/状态函数 | 定向单元测试、组合矩阵、`compileall` |
| Repository/Importer/迁移 | 定向集成测试、事务失败注入、完整 pytest |
| ShadowBot 页面读取或动作 | 成功基线、非默认视口、失败前零副作用；必要时受控实机 |
| 最终确认、phase 或 UNKNOWN | 受控 UNKNOWN、唯一 RECONCILE、写锁和数据库回读 |

不能因为修改了 Markdown 就启动真实 COMMIT；也不能因为单元测试通过就宣称页面
元素、影刀运行或平台副作用已验收。

## 6. 性能优化的正确边界

优化前先记录：

- 冷态或暖态；
- 登录和页面准备；
- 刷新；
- `END/HOME` 加载；
- 全面扫描；
- 目标匹配和轨迹计算；
- 每项资料修改、最终确认和独立回读；
- Importer 和归档；
- 总耗时、扫描次数和滚动次数。

允许删除的是重复初始化、重复扫描和没有独立安全价值的等待。不得删除的是：

- 主动刷新和必要加载；
- 全目标唯一匹配；
- 首次写入前的全批次门禁；
- 最终确认前身份核对；
- 每项独立回读；
- phase、写锁、Importer 验证和 UNKNOWN。
