# PRA 任务风险分级、审查门禁与复杂度治理指南

**版本：** v0.1  
**日期：** 2026-07-31  
**状态：** 评审草案  
**适用范围：** PRA 核心服务、Automation Service、ShadowBot/影刀执行层、平台 Adapter、Web 主控、运行态数据库、测试和文档

## 1. 文档目的

本指南用于解决以下开发治理问题：

- 不同风险等级的任务使用同一套严格审查标准，导致低风险功能开发成本过高；
- 功能完成后才逐轮扩大审查范围，形成多轮补丁和测试重复；
- 为满足审查而增加状态、摘要、锁和恢复路径，新增控制代码又产生更多待审查组合；
- 每次小修改都重复执行全量回归、冒烟、构建和双平台 CI；
- 当前单平台实现即将进入多平台阶段，需要保留平台无关核心，而不能把多平台与分布式高可用混为一谈。

本指南不降低真实平台操作的安全底线，也不修改已经冻结的任务合同。它规定后续任务在计划、实现、测试和审查阶段应如何按风险投入工程成本。

## 2. 决策基线

后续 PRA 开发采用以下基线：

1. **多平台是近期明确目标，必须继续作为架构和审查硬标准。**
2. **真实平台写操作是最高风险边界。** 改价、上下架、库存写入及其恢复逻辑必须严格审查。
3. **人工直接在小程序或 App 中操作属于正常运营场景，不视为异常人员行为。** 系统必须识别由此造成的平台状态漂移，不能盲目覆盖人工操作。
4. **保密要求实行最低必要安全线。** 凭据不得进入仓库和日志，但现阶段不建设企业级密钥治理体系。
5. **每个任务在计划阶段确定审查等级。** 审查和测试投入必须与风险相称。
6. **如非必要，不增加系统复杂度。** 新增控制机制必须证明其必要性。
7. **第一轮审查负责尽量冻结完整阻塞清单。** 后续复审原则上验证原问题是否关闭，不无限扩大范围。

## 3. 核心治理原则

### 3.1 多平台兼容与分布式复杂度分离

多平台兼容要求公共核心不得隐含单平台假设，但不自动要求实现分布式高可用。

公共核心至少必须区分：

```text
platform_name
account_id
internal_sku
platform_product_identity
operation_id
execution_attempt_id
```

必须满足：

- 不同平台和账号的任务、观察、操作、写锁和对账互不串用；
- 平台特有页面、登录、定位和动作逻辑只存在于 Adapter/Executor；
- 公共业务服务通过平台能力接口工作，不依赖具体页面元素；
- 一个平台注册失败不得无条件阻塞其他平台；
- 不创建跨平台混合写批次，除非后续有明确业务需求并单独评审；
- 多平台不等于跨平台原子事务，也不等于多机器自动接管。

只有在真实出现第二个并发执行节点、跨机器接管需求或单机故障无法接受时，才评估分布式租约、外部锁服务或消息总线。

### 3.2 平台事实、系统意图和执行历史分离

权威关系固定为：

| 数据 | 权威来源 |
|---|---|
| 系统准备执行什么 | PRA 任务与操作账本 |
| 系统曾经执行过什么 | PRA 执行记录、回执和审计事件 |
| 平台当前真实价格、库存和上下架状态 | 真实平台重新读取结果 |
| 为什么出现差异 | 对账事件、人工说明和执行证据 |

本地数据库保存意图、历史和证据，不应被当作真实平台当前状态的绝对权威。

### 3.3 人工外部介入是一等场景

员工可能绕过 PRA，直接在小程序或 App 中修改价格、库存或上下架状态。所有真实写操作应优先采用：

```text
执行前读取
→ 比较预期旧状态
→ 执行写操作
→ 执行后重新读取确认
```

建议统一使用以下结果分类：

```text
EXTERNAL_DRIFT
MANUAL_CHANGE_DETECTED
ALREADY_APPLIED_EXTERNALLY
PLATFORM_STATE_UNKNOWN
NEEDS_RECONCILIATION
```

默认处理规则：

- 平台仍符合预期旧状态：允许继续执行；
- 平台已经达到目标状态：记录为已外部完成，不重复写入；
- 平台状态被人工改成其他值：停止自动覆盖并请求确认；
- 无法确认平台状态：不执行第二次写入，进入对账；
- 对账完成前，不把本地期望状态强行回写为平台事实。

### 3.4 最低必要保密线

现阶段保密不是最高审查重点，但以下底线继续强制：

- 账号、密码、Token、Cookie 和私密回调凭据不得提交到 Git；
- 日志、通知、测试夹具和异常堆栈不得输出完整凭据；
- 凭据保存在 `local_env`、操作系统凭据或受控本地配置中；
- 生产账号和测试账号配置分离；
- 员工账号使用平台允许的最低必要权限。

现阶段不强制：

- 自建密钥轮换服务；
- 企业级密钥管理系统；
- 所有低价值业务字段脱敏；
- 每次文档或纯逻辑修改都重新执行完整 Secret Scan；
- 为内部低价值数据建设复杂权限审计系统。

Secret Scan 应至少在以下场景执行：

- 修改凭据加载、日志、通知或配置代码；
- 准备正式 Release；
- 发现疑似凭据泄漏；
- CI 基线或仓库公开范围发生变化。

## 4. 必要性原则：如非必要，不增加系统复杂度

新增数据库表、字段、状态、锁、摘要、版本、缓存、恢复流程、兼容路径或跨模块关系前，必须证明其必要性。

只有同时满足以下条件，才允许增加新的控制机制：

1. 对应一个当前真实存在或近期明确会出现的风险；
2. 该风险可能导致真实平台误操作、人工操作被错误覆盖、重复副作用、关键数据损坏、多平台数据串扰或当前系统无法恢复；
3. 现有机制和更简单的运行规则无法合理解决；
4. 新增复杂度与风险降低程度相匹配；
5. 已明确测试范围、维护责任、失效处理和未来删除条件。

不得仅因以下理由增加复杂度：

- 理论上更加完整；
- 未来可能用到，但没有明确任务或时间表；
- 可以增加更多审计信息；
- 可以覆盖极低概率且可低成本人工恢复的异常；
- 为了让合同、模型或状态机形式上更对称；
- 为了修复新控制机制自身引入、但原系统不存在的问题。

新增机制前必须回答：

> 不增加这项机制，当前或近期明确支持的场景会发生什么具体事故？

如果答案只是“理论上可能不够严谨”，通常不应增加；如果答案是“可能重复改价、覆盖人工操作、串用其他平台数据或损坏关键账本”，则具备必要性。

### 4.1 方案优先级

存在多个可行方案时，按以下顺序选择：

1. 明确运行约束；
2. 人工确认或人工恢复；
3. 复用现有机制；
4. 局部校验；
5. 新增全局状态、持久化字段或控制流程。

示例：

| 风险 | 优先方案 |
|---|---|
| 同一账号被两个执行器同时操作 | 每平台账号只允许一个写 Worker |
| 人工修改导致状态漂移 | 写前读取、写后确认和定时对账 |
| 重复改价 | operation ID、提交意图和提交后复查 |
| 服务崩溃后状态不明 | UNKNOWN + 唯一只读 RECONCILE |
| 多平台页面差异 | Adapter 与能力声明 |
| 低概率自动恢复困难 | 明确人工恢复手册 |

### 4.2 新增与删除对称

每增加一种控制机制，必须检查能否删除、替代或合并已有机制。

审查不只问“还缺什么”，也必须问：

> 现在哪些代码、字段、状态或兼容路径已经多余？

保护层不得只增不减。

## 5. 任务审查等级

每个任务必须在计划或 Goal 中声明一个 `Review Profile`。

### 5.1 R1：轻量审查

适用：

- 文档；
- UI 文案和纯展示；
- 独立纯函数；
- 不写业务事实的报表格式；
- 不改变合同的重命名或小型整理。

要求：

- 相关静态检查；
- 必要的局部测试；
- 不要求全量回归和系统冒烟。

### 5.2 R2：普通审查

适用：

- 只读平台 Adapter；
- 数据解析和导入预览；
- 商品映射；
- 普通业务规则；
- 非关键数据库读取；
- 不触发真实副作用的 Web 功能。

要求：

- 模块测试；
- 直接依赖测试；
- 一次 CI；
- 多平台身份和平台能力边界检查。

### 5.3 R3：严格审查

适用：

- 改价、上下架或库存写入；
- 平台执行器；
- 人工审批；
- UNKNOWN/RECONCILE；
- 数据库迁移；
- 多平台公共写入接口；
- 可能覆盖人工平台操作的功能。

要求：

- 模块测试；
- 受影响集成测试；
- 副作用幂等测试；
- 人工外部介入和状态漂移测试；
- 多平台/账号隔离测试；
- 合并前全量 CI；
- 需要时进行受控实机验收。

### 5.4 R4：架构级审查

适用：

- 连接两个或多个权威模块；
- 重构操作账本；
- 改变任务状态机；
- 改变平台事实与本地事实的权威关系；
- 修改公共契约；
- 多平台调度和执行控制面；
- 引入跨模块恢复、租约或统一写锁。

要求：

- 编码前完成设计审查；
- 冻结当前部署假设、故障模型和非目标；
- 明确复杂度预算；
- 集成、恢复、状态漂移和多平台隔离测试；
- 全量回归与系统冒烟；
- Linux/Windows CI；
- 第一轮代码审查尽量形成完整阻塞清单。

PR #24 的 Automation Service 控制面连接 Automation Run、任务 13 快照、ProductObservation、影刀 UI 写锁和脉冲覆盖，属于 R4。其严格审查有合理性，但以后类似任务应在编码前声明 R4，而不是在功能完成后逐步提高标准。

## 6. 任务计划中的审查配置

每个任务计划至少包含：

```text
Review Profile: R1 / R2 / R3 / R4
真实平台写操作: 是 / 否
涉及平台: 列表
涉及账号: 列表或隔离规则
连接权威模块: 列表
人工外部介入风险: 描述
最坏事故: 描述
人工恢复成本: 低 / 中 / 高
允许新增表: 数量
允许新增持久化状态: 数量
允许新增跨模块关系: 数量
测试范围: 模块 / 集成 / 全量 / 实机
明确非目标: 列表
```

任务开发中若超过计划中的复杂度预算，必须暂停扩展并重新评审设计，不能默认继续叠加控制代码。

## 7. 审查严重度与阻塞规则

### 7.1 必须阻塞合并的问题

以下问题原则上属于 P0/P1：

- 可能对错误平台、错误账号或错误商品执行写操作；
- 可能重复改价、重复上下架或重复写库存；
- 可能覆盖员工在真实平台上的人工操作；
- UNKNOWN 后可能触发第二次不安全写入；
- 多平台或多账号数据可能串扰；
- 绕过人工审批、任务有效性或价格下限；
- 可能损坏运行态数据库或丢失关键执行事实；
- 当前声明支持的部署方式无法运行；
- 明文凭据进入仓库或日志。

### 7.2 通常不阻塞当前任务的问题

以下问题默认记录为 P2、技术债或后续增强：

- 只影响未来未承诺的多实例无缝接管；
- 极低概率且可低成本人工恢复；
- 不影响真实平台动作的形式化不对称；
- 非关键事实缺少额外摘要；
- 历史兼容路径尚未覆盖尚不存在的数据；
- 企业级保密、自动轮换或复杂审计能力；
- 仅为未来分布式架构预留的机制。

R4 任务可以将其中一部分升级为阻塞项，但必须在计划或第一轮审查中说明原因。

## 8. 审查范围冻结与停止规则

### 8.1 第一轮审查

第一轮审查负责：

- 对照 `Review Profile`；
- 检查真实平台副作用；
- 检查人工外部介入后的状态漂移；
- 检查多平台和账号隔离；
- 检查任务合同、数据库和恢复路径；
- 尽量一次性列出完整阻塞清单；
- 明确哪些问题不在当前任务范围。

### 8.2 后续复审

后续复审原则上只验证已列问题是否关闭。

复审中新发现的问题，只有满足以下条件之一，才新增为阻塞项：

- 会错误操作真实平台；
- 会覆盖人工操作；
- 会重复真实副作用；
- 会造成数据库损坏或关键事实丢失；
- 会破坏多平台/账号隔离；
- 会绕过审批或价格安全边界；
- 会导致当前支持的部署方式无法运行。

其他问题进入技术债，不得形成无限追加 P1 的审查循环。

### 8.3 触发重新设计

出现以下任一情况，应暂停补丁式修复并重新设计：

- 审查修复新增的生产代码接近或超过原功能代码；
- 为一个风险连续增加多层状态、摘要和回退路径；
- 同一任务超过三轮复审仍不断出现新的结构性阻塞项；
- 测试数量快速增加，但主要用于证明新控制代码本身；
- 新机制需要兼容旧机制、而旧机制又无法删除；
- 无法用简短语言说明当前唯一事实来源和恢复路径。

## 9. 测试分级与执行时机

测试代码和测试时间不是越少越好，但必须避免重复执行同一门禁。

### 9.1 开发过程中

- 只运行改动模块和直接依赖测试；
- 优先使用单元和小型集成测试；
- 不要求每次小修改都构建 wheel、执行系统冒烟和双平台 CI。

### 9.2 提交审查前

| Review Profile | 最低测试要求 |
|---|---|
| R1 | 静态检查 + 必要局部测试 |
| R2 | 模块测试 + 直接依赖测试 |
| R3 | 模块 + 受影响集成 + 副作用/漂移测试 |
| R4 | 模块 + 集成 + 恢复 + 多平台隔离 + 全量回归 |

### 9.3 Ready for review / 合并前

- R1/R2：CI 按变更范围执行；
- R3：运行一次全量 CI，必要时系统冒烟；
- R4：运行一次完整回归、系统冒烟和 Linux/Windows CI；
- 实机测试只用于真实 UI、副作用或环境相关行为，不能由纯单元测试替代；
- 已通过且 Head 未变化的 CI 结果不应由审查端无理由重复执行。

### 9.4 Release 或部署

以下门禁集中在 Release 或部署阶段执行，而不是每个小补丁都执行：

- wheel/sdist 构建；
- 仓库外隔离安装；
- 完整 Secret Scan；
- 证据摘要复算；
- 全量实机验收；
- 备份和恢复演练。

涉及打包、凭据、部署脚本或证据合同的变更除外。

## 10. 复杂度预算

复杂度预算不是固定代码行上限，而是设计告警机制。

计划阶段应估计：

- 新增生产代码；
- 新增测试代码；
- 新增数据库表和字段；
- 新增持久化状态；
- 新增摘要或版本身份；
- 新增跨模块关系；
- 新增恢复路径；
- 新增文档和手工验收步骤。

触发重新评估的信号包括：

- 测试和控制代码明显超过业务实现，且风险并非 R3/R4；
- 一个新功能需要新增多张表、多个状态机和多套摘要；
- 为兼容旧控制机制而建立第二套控制机制；
- 一个异常路径产生比正常路径更多的代码和状态；
- 后续维护者需要同时理解多个等价事实来源。

R4 任务可以拥有较高测试和控制代码占比，但必须在计划阶段说明原因。

## 11. 防止控制复杂度螺旋

控制复杂度螺旋的典型过程是：

```text
为了防止一个异常
→ 增加状态、字段、摘要或锁
→ 新机制产生新的组合和异常路径
→ 增加更多测试和恢复逻辑
→ 审查新增控制代码
→ 再增加控制代码
```

防止方法：

1. 先执行必要性门禁；
2. 优先采用运行约束和人工恢复；
3. 为任务设置复杂度预算；
4. 第一轮审查冻结阻塞范围；
5. 每增加一种控制，检查能否删除一种旧控制；
6. 区分当前部署需要与未来理论保证；
7. 复审不无限追加低概率阻塞项；
8. 复杂度超过预算时重新设计，而不是继续打补丁。

## 13. 采用方式

1. 本指南合并后，后续新任务在 Goal 或计划文档中声明 `Review Profile`。
2. R4 任务必须先完成设计审查再编码。
3. 已冻结合同和已合并实现不会因本指南自动降级或删除；如需简化，应单独创建重构任务并证明收益。
4. `AGENTS.md` 是否引用或吸收本指南，应在本指南评审通过后单独决定，避免草案直接升级为强制协议。
5. 后续可根据实际多平台开发和事故数据调整审查等级，但不得绕过真实平台副作用、人工状态漂移和多平台隔离三项最高风险。

## 14. 最终原则

> 按任务风险预先确定审查等级；长期保证多平台兼容；最高强度集中在真实平台副作用和人工介入后的状态漂移；保密保持最低安全底线；如非必要不增加系统复杂度，并防止控制机制为了证明自身正确而持续膨胀。
