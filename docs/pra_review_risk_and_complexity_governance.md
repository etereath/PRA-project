# PRA 项目审核治理规范 v2.1

文档类型：Review Governance。修订日期：2026-09-06。

本版修订 v2.0，整合仓库已有的风险分级、复杂度与冷启动补充。主维护路径仍是 `docs/pra_review_risk_and_complexity_governance.md`；已合入 main 的版本为仓库现行规范，PR 中的修订按明确采纳范围使用。新版本不自动撤销历史验收、不自动扩大进行中任务的 blocker，也不授予合并或平台操作权限。

业务主定义见[业务合同](business_contract.md)，职责与实现门槛见[目标矩阵](rebaseline/task13_6_target_responsibility_and_gap_matrix.md)，现状见[实现图](rebaseline/task13_6_current_implementation_map.md)与[当前状态](project_current_status.md)。本文规定如何判断和验证，不复制第二套业务合同。

## 1. 目的

审核判断系统能否以合理复杂度完成真实经营任务，并在必要安全边界内可靠运行。三个同级目标始终同时考虑：

| 目标 | 必须回答 |
|---|---|
| 业务可行性 | 正常任务能完成吗？阻塞、失败和重启后有明确后续吗？经营者知道结果和下一步吗？ |
| 安全与正确性 | 授权、身份、事实来源和副作用是否正确？会不会重复写、覆盖人工操作或重复记账？ |
| 开发与维护效率 | 能否复用已有能力？恢复和日常操作是否可承担？新增控制是否比问题本身更复杂？ |

组件正确不等于系统正确；Fail Closed 不等于业务完成；CI 全绿不等于 Stage Goal 通过。审核不以问题数量、测试数量或新增控制数量衡量价值。

## 2. 审核基本原则：目标与证据分开

先明确本次交付承诺的经营结果，再沿正式入口与直接调用链核对；不因为有同名类、Schema、报告或测试就认定业务接线成立。

| 要判断什么 | 主要依据 | 不可替代的区别 |
|---|---|---|
| 应该怎样经营 | 最新明确业务裁决与承接它的 Canonical 合同 | 旧代码不能否定新业务目标；历史方案可以修订 |
| 当前实现怎样运行 | 指定 SHA 的生产入口、调用关系、持久化与恢复路径 | 目标架构、PR 描述、实现报告不是代码证据 |
| 已验证什么 | 对应版本、输入、环境与覆盖范围的测试、CI、实机记录 | 代码存在、CI、实机、部署和长期运行分别证明 |
| 平台实际是什么 | 合格平台观察及其身份、时间、scope、粒度和完整性 | Intent、管理员确认和 SQLite 期望值不能自动成为平台事实 |
| 现场运行哪个版本 | 部署与运行证据 | 已合并不代表已部署 |

新任务或完整实现审查实际读取最新 main/PR Head、PR/Issue 正文与评论、changed files、提交、适用 AGENTS、相关文档、正式源码、测试和 CI。历史问题需复核它在当前路径是否仍成立。复审仍读取最新 Head，但按第 10 节限制展开范围。

报告列明核验 SHA、实际读取范围和证据限制。权限或环境不足时写明未验证内容，不以旧摘要代替，也不把“未看到”写成“不存在”。Head 改变后判断哪些证据受影响；只改链接不自动使所有实机证据失效，相关代码/合同改变也不能无说明继承旧 PASS。

## 3. 目标与边界的优先级

真实业务目标 > 必要安全与数据硬不变量 > 总体架构原则 > 当前施工边界 > 当前实现方式。

此顺序用于识别并修改不合理的设计边界，不构成跳过授权、伪造事实或猜测执行的许可。历史聊天解释决策缘由，不是永久施工合同；最新建议也不能仅凭“更新”就覆盖已经验证的事实。

## 4. 硬不变量与设计边界

### 4.1 硬不变量

- 真实写通过正式身份和授权链，保持写前读取、比较预期旧状态、执行、写后确认。外部员工直接修改平台是正常经营，过时 one-shot Intent 不默认写回。
- UNKNOWN 不假定成功或失败后重写；复用既有唯一 RECONCILE，保留执行身份、锁和证据，按正式恢复路径收口。
- 同一经营责任不得由新旧两条 authority 重复扣减或生成正式计划；保留唯一实物库存 authority。合法 shadow 与只读副本不因此变成第二个写 authority。
- 不伪造 authenticated principal，不破坏原始审计证据，不用不可验证的分配决定覆盖权威事实。原证据不可变不等于派生解释永远不能依据新合格证据修正。
- evidence confidence 与 granularity 分开；聚合事实不能任意拆成 SKU 成交事实。业务决定不等于观察证据；可验证的人工材料按其实际证明范围处理。
- 严重度不授予副作用权限，Observation S4 不继承 Emergency S4 的自动下架权限。
- platform_name、account_id、internal_sku、platform_product_identity 的范围不得串用；平台 UI/登录/selector 留在 Adapter/Executor/ShadowBot。
- 凭据、完整 Review token URL、生产配置及 Runtime 数据不得进入 Git、日志或公开证据。采用当前部署足够的保护，不据此强制建设企业级密钥系统。

这些边界不能靠提高管理员等级、改状态名称或增加日志绕过。需要修订硬不变量定义时，必须明确其业务、安全和迁移影响并取得相应裁决；提出重审本身不授权违规操作。

### 4.2 设计边界

表数量、Service 职责、当前状态机、Schema 不变、某模块后置、运行拓扑与 PR 切分通常是设计选择。先判断是否仍服务于本次目标，再决定保留或修改。

“Intent / Task / continuation 职责不同”不推出必须三张表；“优先复用”也不推出永不允许新结构。某阶段纯文档的限制不自动成为后续实现阶段的永久禁令。

## 5. Boundary Conflict 机制

边界妨碍真实目标或硬不变量时，显式报告 `BOUNDARY CONFLICT`，用简短记录说明：原边界与上层目标、指定版本证据、继续遵守的具体后果、最小替代方案及代价。

不要增加旁路掩盖冲突。常规实现选择在已授权范围内由实施者解决并记录；改变业务口径、权限、authority 或显著扩大阶段范围的决定交负责人裁决。已明确采纳的决定不重复索要许可。只暂停受冲突影响的部分，能独立完成的已授权工作继续。

## 6. 按任务类型选择审核方式

Task Type 表示正在交付什么，Review Profile 表示影响范围和风险，两者单列；R1～R4 见第 19 节。

| Task Type | 主要审核单位与出口 |
|---|---|
| Architecture / Planning | 经营旅程、责任、失败/恢复、复用与首切片；不预先冻结每个 SQL 字段、Route、错误码和内部类 |
| Module / Implementation | 组件承担的业务职责及实际交接、权限/事务/幂等和直接回归；不能只核对类内部 |
| Integration / Cutover | 同一 Runtime 的正常、阻塞、重启、UNKNOWN 与终态旅程，及适用的 authority/Web 切换 |
| Bugfix / Re-review | 已冻结问题、复现、修复与直接回归；不借修复重审整个项目 |
| Documentation / Governance | 语义、来源、入口一致性、权限和阶段表达；只有相关理解或运行行为改变时追加相应验证 |

一个 PR 可同时包含模块实现和集成责任。整体计划中的后续能力，只有在本切片明确支持或直接受改动影响时才成为本次门槛。

## 7. 注意力预算与开工输入

开工先说明本切片用户结果、范围与运行约束、优先复用资产、主要风险及验收证据。复用审计与最小设计可以直接写在实现 PR 中；已有批准架构不要求重新开总纲或重复 G1/G2。

每轮聚焦最重要的 3～5 个问题类别，这不是截断真实 blocker 数量的上限。首次尽量完整检查已承诺旅程；未读到关键路径就说明范围不足，不声称全量审查完成。

候选问题必须关联本期具体后果。纯理论对称性、无明确需求的未来部署和可选审计增强不升级为当前 blocker；有效观察可以保留为非阻塞后续项。

## 8. 严重度、阻塞与证据缺口

严重度描述问题影响，是否阻塞以及在哪个交付点阻塞必须另写，不能只用数字代替判断。

| 分类 | 判定 | 默认处置 |
|---|---|---|
| P1 | 有证据证明当前承诺的核心业务不能完成、出现越权/重复副作用/关键事实损坏，或复杂度与人工成本严重破坏可交付性 | 阻止受影响交付；说明实际路径、触发条件和结果 |
| P2 | 存在明确业务、安全或维护影响，但有可执行临时路径且不破坏当前核心目标 | 默认非阻塞；记录临时路径、接手者与触发条件。若确需阻塞，单列具体交付理由，不能要求所有 P2 无条件清零 |
| P3 | 不影响当前目标的文字、局部体验或可选增强 | 非阻塞；不因为“想得到改进”就必须新建任务 |
| Merge Gate | 当前合并确实要求的 CI、构建、迁移、冒烟或外部证据未满足 | 列明要求来源、适用对象/版本与解除条件；不凭审查偏好新增门禁 |

缺少实机记录、尚未读取关键代码、测试覆盖未证明，不自动等于已发现 P1，也不允许宣称能力成立。根据证据将 Stage Goal 标为 NOT YET VALIDATED；若缺的是适用的强制合并证据，同时列 Merge Gate。发现可复现的业务断链则按影响列 P1/P2，不能用“未验证”掩盖已证实失败。

一个根因优先一个问题编号，写出业务、安全和效率影响，避免以多个角度重复计数。

## 9. 双结论制度

较大实现审查必须分别给出：

- **Implementation Review**：P1、P2、Merge Gate 数量与具体项；区分阻塞 P2、非阻塞 P2及未覆盖范围。
- **Stage Goal Validation**：PASS / FAIL / NOT YET VALIDATED，并写明所指的切片、版本和环境。

PASS 表示对应目标所需证据充分；FAIL 表示有证据证明目标不成立；NOT YET VALIDATED 表示证据不足或所需验收尚未进行。文档理解 PASS 不代表功能 PASS，隔离旅程 PASS 不自动代表实机或部署 PASS。

可以得出“0 P1 / 0 P2 / 0 Merge Gate，Stage Goal NOT YET VALIDATED”，但必须说明审查覆盖范围和下一次验收缺什么。NOT YET VALIDATED 不自动决定可否合并；按该变更实际合并门槛判断，不能豁免既定现场证据，也不把所有后续验收一律提前成当前代码合并门槛。

未完成关键实现审查时明确写未完成，不以 0 个已发现问题暗示全量通过。建议合并、实际合并、启用新 authority、部署、平台写入是不同动作，分别依已有授权处理。

## 10. 冻结 blocker 与复审范围

首次完整审查尽量一次冻结 blocker。每项包含稳定编号、版本/路径、触发情景、具体影响、最小修复目标和验证条件；冻结的是问题及结果，不是审核者偏好的表名或补丁。

复审核对原问题、修复直接影响的路径和相关新 Head CI，不重新扫描所有未来功能。新增 blocker 仅限：修复破坏硬不变量、使当前核心目标失效，或新证据证明原审查依据错误等真正高风险问题。必须说明为何属于例外及其证据，不能以“R4”或理论可能性代替。

已冻结为阻塞的 P2 不因本版“默认非阻塞”而自动关闭。调整其处置须依据当前影响与临时路径记录理由，不能靠修改标签绕过原问题。

用户明确说“这是完整实现，请重新审查”时，重新完整审查该交付范围，不受上一轮问题清单限制；这不等于重新批准所有历史业务设计。

多轮修复出现同一根因和不断新增的控制链时，暂停该处补丁，重新审视边界和更简单方案。轮次与代码量是诊断信号，不是自动失败或强制重构的数值阈值。

## 11. 复杂度治理与最薄纵向切片

新增表、字段、状态机、锁、Service、Summary、version、缓存或恢复链之前回答：**不增加它，当前或近期明确支持的业务会发生什么具体事故？**

同时说明已有机制为何不足、最小方案、验证成本及维护责任。优先顺序：明确运行约束 → 可执行的人工确认/恢复 → 复用既有能力 → 局部校验 → 必要的最小持久结构。人工恢复须满足第 12 节，不是用“以后找人”替代 owner。

逻辑责任不等于物理结构数量。不能只因理论完整、形式对称、未来可能有用或方便审计就新增；也不能仅凭“多了一张表”拒绝已经证明必要的持久交接。优先复用现有 v4/v5、Queue、Worker、Importer、Watchdog、锁、UNKNOWN/RECONCILE、Review/Outbox、Task/history 和库存 ledger。

先让一个业务对象经过正式 Web、授权、执行、结果与恢复，再扩展能力；Web 随切片接入。开发者在现有实现 PR 中完成局部复用分析后继续施工，不停在重复计划。小步提交用于持续连接和验证，不能长期把核心交接推到“最后集成”。

新增控制时检查哪些旧控制可合并或退役；没有证据不为对称性强删旧设施。异常路径、摘要或测试迅速膨胀时检查是否在证明新控制自身；不按代码行数或测试占比直接判定过度设计。

## 12. 业务生命周期责任原则

每个非终态对象都应说明：当前 owner、下一步、触发、失败、重启、最终收尾。责任可以在人或现有组件，不要求每段新建后台服务。

| 阶段 | 合法责任与恢复 |
|---|---|
| 未最终授权的 PENDING / preparation | Human + Web，下一触发是明确 prepare/confirm/submit、取消、替代或过期。短时 preparation 重启失效可以重新确认；后台不补授权 |
| 系统接受最终确认的边界 | 必须能从持久事实判断已可靠接手、跟踪既有执行、明确要求重新确认或终止；不能只剩 audit 而永远不知道下一步 |
| 已形成持久 continuation，等待 blocker | 明确的长期 owner 周期重评估并在授权仍有效、事实合格时推进；失效/漂移则持久记录重新确认或终止并交回人；重启能重新发现 |
| 已发布 / 结果未知 | 复用执行 ledger、Queue、Importer/Watchdog 与唯一 RECONCILE；跟踪既有执行身份，不因重启或新 Intent 盲目再次发布 |
| 转人工处置 | 原因、待办对象、承担角色、可达入口、解决/超时/终止规则明确；解决后系统能关联原对象继续或收尾，不能只有日志或无人负责的页面 |

持久化 PREPARED 批次并不自动等于最终授权，授权 history 也不自动等于完整恢复合同。确认后的合法重新确认必须有持久原因和可发现入口，不能退回依赖用户偶然再次点击。

已授权执行中的确定性恢复不能依赖未来 Agent 在线。单对象或组件可恢复业务异常应被隔离；DB/schema/process 根本故障可以使宿主明确 FAILED，不能要求无条件吞异常并假装健康。周期重评估是合法触发，但必须有正式接线、可发现对象和重启证据，而不是“下次扫描也许顺便处理”。

## 13. 测试证据按任务类型匹配

| 交付内容 | 所需证据方向 |
|---|---|
| 架构/业务文档 | 具体业务例、责任交接、数量/时间与权限语义；按实际改动进行理解验证 |
| 机械文档/链接 | 严格 UTF-8、链接和预期差异；不新写镜像文案的测试 |
| 模块实现 | 有意义的行为、权限/事务/幂等及直接依赖测试，按实际触及的风险选择 |
| 执行集成 | 同一 Runtime、正式 Service/Repository/file Queue/Importer 的正常旅程，适用的 blocker、重启和 UNKNOWN 恢复 |
| Authority cutover | 旧 authority 停止、baseline 对齐、新 authority 与 Web 同 gate 生效、跨日/恢复/回滚无重复记账 |
| Bugfix | 原问题复现、修复及直接回归，不借机重做完整验收 |

测试的层次与替身范围必须说明。单测使用 mock 合法；要证明跨组件接线时，只替换受控外部 UI/平台边界，不能把待证明的 Authorization→publisher、Coordinator→Queue 或 result→Importer 替换成成功 stub。多个孤立测试的 PASS 不能拼成完整旅程 PASS。

集成应覆盖正常完成、适用 blocker 与服务重建/进程退出；同一情景可以同时证明 blocker 解除和重启恢复，不要求为了表格重复三套等价测试。没有合格平台回读，不能只凭请求已发或 Worker 声明成功判定经营结果完成。

真实 UI、平台行为、部署兼容或当前阶段明确要求的实机旅程，仍需对应现场证据。缺少环境/授权时先完成可审查实现和隔离验证，记录所缺证据与现场接手者/触发条件；不得拿更多 mock 代替实机，也不为等实机而停止所有可完成工作。

## 14. 容易误判的情景

以下用于检验审查推理；精确业务条件继续按业务合同和目标矩阵，不新增状态或接口。

| 情景 | 正确判断 |
|---|---|
| Task 等人工明确授权，重启后短时准备失效 | 可以合法；核验人工下一步与有效期，不强制 Coordinator 自动执行 |
| 已最终确认，仅有 audit，重启无法判断发布或重确认 | 责任缺口；查实际持久交接，不能以安全停住就结束 |
| 新事实只 shadow，旧链独占经营 authority，Web 读旧链 | 合法切换前姿态；shadow 不能冒称新业务 authority 已启用 |
| 两套链同时扣减/生成正式计划，或新 authority 已启用而当前 Web 仍读旧事实 | 前者双 authority，后者切读不完整；分别定位，不混为一个状态 |
| 聚合数量可信，但缺少 SKU 归属 | 保留合格聚合事实与缺失粒度；人工分配不升级成事实，也不自动触发执行 UNKNOWN/锁/RECONCILE |
| 当前下架了 B 或映射改成 1:1 | 不证明整个累计观察期间只属于 A；必须核对完整时间覆盖，不能重写此前归属 |
| 本地期望与平台不同，或平台已被员工改到目标 | 使用合格回读判断漂移/已完成，不能为维持旧 Intent 反复写回 |
| 纯改价首切片仍未实现 Closing/Health/第二平台 | 按本切片目标判断；未触及后续能力不是本期缺陷，缺少当前价格执行 owner 则不能延期掩盖 |

## 15. Review Stop Rule

审查在能够给出有证据、范围清楚、下一步明确的判断时结束，不以所有工作已经完成作为结束一次审查的前提。

- 可交付：阻塞 P1/P2 已解决，适用 Merge Gate 满足；非阻塞 P2 有合理处置，Stage Goal 及证据范围明确。停止可选测试和扩题。
- 需修复：冻结具体 blocker 后返回实施者。审核者不为了等待修复继续挖无关问题。
- 待验收：说明缺少的版本/环境/证据、owner、触发与当前允许推进的工作，保持 NOT YET VALIDATED；不无限重跑本地测试。
- 已证实目标失败：返回 FAIL 和具体后果，按需要修复或做 Boundary Conflict；不能通过降成“未验证”结束问题。

复审只按第 10 节。明确列为非阻塞的 P2 不因停止规则再次变成必须清零；真实硬不变量破坏也不因“轮次够了”而放行。

## 16. 标准审核输出

较大任务使用以下最小结构，简单变更可压缩成短段落：

```text
Task Type / Review Profile：
核验版本与实际覆盖范围：main / PR Head / 环境 / 证据限制
Core Goal 与本轮重点：
Boundary Conflict：无 / 具体冲突及最小方案
Findings：编号、证据/触发、影响、修复目标、验证条件、是否阻塞
Implementation Review：P1 / P2（阻塞与非阻塞）/ Merge Gate
Stage Goal Validation：PASS / FAIL / NOT YET VALIDATED，所指范围
Efficiency Assessment：复用与新增控制是否必要
Next Action：实施者、审核者或负责人，下一动作与触发
执行记录：是否修改远端、是否合并、是否进行平台操作
```

不是每项发现都要新增文档、Issue 或审批。尽量在原 PR 留下可复核记录，避免多份内容相近的规范。

## 17. 对 13.7 开发策略的应用

首切片按[人工改价计划](plans/task13_7_human_update_price_vertical_slice.md)：1 SKU、一次人工 UPDATE_PRICE，连接有效决定、Task、正式授权、持久交接、既有 v4/Queue/Worker/Importer、终态和回读，并验证重启或 blocker 恢复。具体代码现状每轮读取，不把本例当成实现完成声明。

首次实现审查重点是：新有效决定能否先记录；授权到持久接手是否可靠；blocker 解除/重启后谁继续；已有发布与 UNKNOWN 是否避免重复写；经营者能否看到有依据的结果。新表数量和类名不是首切片目标。

Exposure、Supply、Commitment、Closing、Health 及 authority cutover 随相关切片验收，不能把所有 IG 一次前置到纯改价；也不能因后续阶段存在而遗漏当前切片的核心责任。两处 Exposure/实物上限按实际受影响范围处理，不机械捆绑纯改价。

当前 Human 是销售 Controller；14-A 负责集成与冻结，14-B 首版负责诊断和受控风险中性工具，不成为销售 Controller 或确定性恢复 owner。多平台保留公共身份和能力边界，第二平台前完成组合层设计；不因此要求当前实现分布式执行或复杂 Exposure Allocator。

## 18. 实施者、审核者与负责人

实施者负责最小设计、代码、测试、必要迁移/运行说明和绑定版本的证据；完成已授权工作，不用反复生成计划代替实现。审核者独立核对业务与代码，给修复结果要求而非强制自己偏好的架构。负责人裁决真实业务分歧、现场验收与需要的权限。

当前由 Codex 开发、ChatGPT 审核是协作安排，不改变 PRA 产品中的授权主体。审核者准备交接文档或提出补丁后，应说明参与范围；实施者自检不得冒称独立复核。

用户授权在会话内持续有效；常规可逆工作、文档措辞和已授权分支提交不反复请求确认。检查 branch/worktree，保留并行改动；审查与规范修订不直接覆盖正在施工的分支。开 PR、建议合并、结束 Draft、merge、部署和真实平台操作分别判断授权，未经明确要求不 merge 或结束 Draft，最终报告实际执行情况。

## 19. 风险等级与验证投入

| Review Profile | 影响范围 | 审核投入 |
|---|---|---|
| R1 | 机械文档、低影响展示、局部纯逻辑 | 静态/局部检查，必要时小测试 |
| R2 | 普通只读、解析、业务规则 | 模块与直接依赖、事实口径和身份范围 |
| R3 | 真实写、授权、迁移、UNKNOWN/RECONCILE | 受影响集成、权限/幂等/漂移/恢复及适用现场证据 |
| R4 | 公共合同、authority、跨模块责任/恢复架构 | 目标与责任设计、复杂度及实际交付所需跨组件证据 |

文件格式不决定等级。只读代码若决定 authority 或写授权，按真实影响提高；R4 架构文档不自动要求生产全量回归或实机，R1 文案也不能掩盖公共合同变更。风险等级不是所有检查项的机械乘数。

开发中优先运行改动与直接依赖测试；完整交付按实际风险补集成/恢复证据。仓库既有 CI、构建、Secret Scan 和证据复算照常执行，不因本文削弱门禁。对于同一 Head、相同相关环境且已通过的检查，审核端无具体理由不重复运行；依赖/环境改变或结果可疑时可针对性重验并说明理由。

打包、隔离安装、完整实机与备份恢复等验证按其相关变更和发布目标安排，不要求每个文字补丁再本地做一遍。需要改变 CI 工作流时作为具体工程变更说明影响，不能通过治理文字静默跳过。

## 20. 文档、冷启动与规则演进

每个主题保留一个主要定义处，README/AGENTS/index/status 是短入口；实现图绑定版本，历史报告保留当时结论。撤回的审核意见退出待修缺陷，历史证据、hash-bound 样本和原样 archive 不为格式改写。轻量变更记录可以放 PR，不另建治理数据库或状态机。

冷启动只在需要证明陌生读者理解时使用，由负责人主持；正式 AGENTS 必须在新会话启动前已置于固定版本工作树。只给 Canonical 阅读集与中性问题，评价业务推理、引用及不确定性，实施者可准备问题但不得自答冒称独立验收。

内容正确性与环境独立性分开。后补读正确 AGENTS 不能消除已注入旧指令；提供答案后的纠错标明定向复核，原答保留。多模型是理解证据，不要求所有模型都 PASS，也不依据不同环境各一次作答排名模型。

默认一次完整验收加失败项/直接影响复核，不无限扩题。先区分文档、题目和推理问题，再修订真正原因；只有语义改变的相关内容重验，链接/补证说明差异即可。文档修复、模型纠错、负责人接受各自记录，不能互相代替。

治理修订说明变更来源、影响及适用范围。进行中的任务不因版本号变化重开总纲、重做已通过 Gate，或补做与本期无关能力；新的硬不变量证据或负责人明确范围变更按第 5/10 节处理。本轮 v2.1 不改变 13.6 已接受结论，不要求暂停 13.7 开发等待本规范 PR 合并。
