# PRA 项目审核治理规范 v2.0

角色：Canonical / Review Governance。Task13.6-3 根据用户提供的 v2.0 原文归位，后附风险配置与开发方法补充；替代本路径 v0.1 草案，不另设第三套治理。

**文档类型：** Review Governance  
**版本：** v2.0  
**生效日期：** 2026-09-01  
**适用范围：** PRA 项目及其派生自动化、运营 Web、Runtime、Automation、Queue/Worker/Importer、Agent 接入等开发任务  
**替代原则：** 本规范替代过去以“安全边界是否被严格遵守”为中心的单一审核方式。

---

## 1. 目的

PRA 的审核目标不是最大化约束数量，也不是尽可能发现更多问题。

审核的目标是：

> **在业务目标、必要安全性和开发效率之间，判断当前设计是否以合理复杂度实现了真实可用、可维护、可恢复的业务能力。**

审核必须同时关注三个同级维度：

1. **业务可行性**
   - 用户真实业务是否能够完成；
   - 正常流程是否能走通；
   - 异常后是否能继续、恢复或明确终止；
   - 页面、后台服务和数据状态是否能够形成实际运营闭环。

2. **安全与正确性**
   - 是否可能越权、重复执行、误写平台；
   - 是否保持数据权威、事务、幂等、并发和审计约束；
   - `UNKNOWN`、写锁、Review、授权等高风险边界是否 fail closed；
   - 是否存在不可逆错误或无法证明的副作用。

3. **开发与维护效率**
   - 实现复杂度是否与业务收益匹配；
   - 是否引入不必要的新状态机、表、服务和兼容层；
   - 正常业务是否需要过量人工重复操作；
   - 一个局部异常是否会产生不成比例的全局停顿；
   - 后续维护和扩展成本是否可接受。

三者不存在默认的绝对优先级。

安全要求不能被用于掩盖业务不可用；业务便利也不能成为破坏必要安全边界的理由。

---

# 2. 审核基本原则

## 2.1 先审“目标是否成立”，再审“实现是否正确”

任何实现都必须先回答：

> 这项能力完成以后，用户实际能够做什么？

只有业务目标成立以后，才继续判断代码、Schema、事务和安全实现是否正确。

不得因为代码完全符合既有施工计划，就自动认为任务目标已经完成。

---

## 2.2 安全停止不等于业务完成

以下行为只能证明系统安全地停止：

- 拒绝执行；
- 保留 `pending`；
- 创建 Review；
- 获取写锁失败；
- 授权失效；
- 进入 `UNKNOWN`；
- Queue 未发布；
- Worker 未执行。

审核必须继续判断：

> 停止以后由谁负责？下一步是什么？是否能够恢复、重新确认或明确终止？

如果一个非终态对象没有明确责任主体和下一步，则业务链仍然是不完整的。

---

## 2.3 组件正确不等于系统正确

Repository、Service、Web、Automation、Queue、Worker、Importer 分别测试通过，不能作为系统闭环已经成立的证据。

跨组件任务必须额外判断：

```text
业务意图
→ 持久状态
→ 调度/授权
→ 执行
→ 结果
→ 恢复/复核
→ 终态
```

任何一个箭头缺失，都属于架构问题。

---

## 2.4 绿色 CI 不代表业务目标通过

CI 只能证明：

> 当前已有测试所定义的合同成立。

CI 不能证明测试没有遗漏系统级责任。

因此最终结论必须区分：

- **Implementation Review**
- **Stage Goal Validation**

两者不得互相替代。

---

# 3. 目标与边界的优先级

发生冲突时，原则上的优先级为：

```text
1. 用户确认的核心业务目标
2. 必要的安全 / 数据硬不变量
3. 总体架构原则
4. 当前阶段施工边界
5. 当前实现方式
```

较低层级的规则不得机械地凌驾于更高层目标。

---

# 4. 硬不变量与设计边界

必须明确区分两类约束。

## 4.1 硬不变量

除非进行明确的高层架构重审，否则不得突破。

典型示例：

- 未获得必要授权不得执行真实平台写入；
- `UNKNOWN` 不得被假设为成功或失败后直接重复写；
- 真实库存不得同时存在两个业务权威；
- 不得伪造 authenticated principal；
- 不得破坏已确认的历史审计事实；
- 不得用不可验证的数据覆盖权威事实；
- 高风险副作用必须具备可追踪身份和幂等边界。

---

## 4.2 设计边界

这些是当前设计的默认约束，而不是不可修改的事实。

例如：

- 当前阶段不新增 Schema；
- 当前阶段不新增 Service；
- 优先复用某现有组件；
- Automation 当前不承担某项职责；
- 当前任务状态机不变；
- 某功能延期到后续阶段；
- 当前 PR 不修改某模块。

设计边界的正确含义是：

> **如果它仍然服务于任务目标，则默认遵守。**

而不是：

> **即使它使核心业务无法成立，也必须遵守。**

---

# 5. Boundary Conflict 机制

审核或开发过程中，如果发现：

```text
既有设计边界
        ↓
与
        ↓
核心任务目标 / 必要安全性 / 合理开发效率
发生冲突
```

必须显式提出：

## `BOUNDARY CONFLICT`

报告至少包括：

- 冲突的原边界；
- 被影响的上层目标；
- 实际证据；
- 如果继续遵守的后果；
- 修改边界的主要方案；
- 各方案的复杂度和风险；
- 推荐方案。

不得：

- 静默突破原边界；
- 为了遵守边界不断增加旁路；
- 通过复杂 workaround 掩盖结构性冲突；
- 因为“计划已经冻结”而继续执行明显错误的方向。

涉及明显架构变更时，应提交给项目负责人决定。

---

# 6. 按任务类型选择审核方式

不存在适用于所有 PR 的统一审核模板。

审核开始前必须先判断任务类型。

---

## 6.1 类型 A：总体架构 / 大任务规划

例如：

- Task 13 总体规划；
- 新业务子系统；
- 新 Agent 架构；
- 新平台接入体系。

### 主要审核目标

优先判断业务逻辑，而不是实现细节。

核心问题限定为：

1. 用户最终希望完成什么真实业务旅程？
2. 从输入到终态分别由谁负责？
3. 是否存在无人负责的状态或组件边界？
4. 正常、失败、恢复三条主要路径是否成立？
5. 模块划分和实施顺序是否合理？

### 本阶段安全审核

只冻结真正需要跨阶段保持的高层不变量，例如：

- 权威数据来源；
- 平台副作用控制；
- UNKNOWN 原则；
- 身份授权边界。

不得过早冻结：

- 每个 Route；
- 每个 SQL 字段；
- 所有 POST 错误码；
- 具体内部 Service 形态；
- 尚无证据需要的 Schema 结构。

### 主要结论

```text
Architecture Goal: PASS / REVISE / FAIL
```

---

## 6.2 类型 B：子任务 / 模块实现

例如：

- 7D 库存；
- 7E 控制面；
- 某个 Importer；
- 某个 Review Service。

### 主要审核目标

1. 是否正确承担上层分配给本阶段的责任；
2. 是否破坏硬安全/数据不变量；
3. 是否出现重复状态机、重复权威或重复执行链；
4. 失败是否可解释和恢复；
5. 实现复杂度是否与收益匹配。

模块审核应同时检查业务、安全和开发效率，不得只审核合同逐条符合性。

---

## 6.3 类型 C：系统集成 / Cutover / 上线

例如：

- 7F；
- 单 Web 正式切换；
- Runtime 真库迁移；
- Automation + Queue + Worker 联动；
- 真实平台验收。

### 主要审核单位

不是类、函数或 Service，而是**真实用户旅程**。

至少检查：

```text
正常流程
常见阻塞
进程重启
超时
恢复
终态
```

典型问题：

1. 一个真实任务能否从创建走到终态？
2. 被 blocker 阻止以后是否能继续？
3. Web / Scheduler / Worker 重启后能否恢复？
4. 超时后是否进入正确状态并要求正确的人处理？
5. 操作员能否看懂当前状态、原因和唯一下一步？

集成审核必须优先采用同一 Runtime、同一组正式 Service 的跨组件验收。

不得使用多个孤立单测的通过结果拼接成“系统闭环已经验证”。

---

## 6.4 类型 D：Bugfix / 整改 PR

### 主要目标

保持审核收敛。

首次审核冻结 blocker 后，复审原则上只检查：

- 冻结 blocker；
- 修复直接引入的回归；
- 真正的新硬安全/架构问题。

不得因为修复一个问题而无限重新审查整个项目。

这是防止 LLM 出现“不断审核 → 不断发现新问题 → 不断扩大合同”的主要机制。

---

# 7. 注意力预算

LLM 和人工审核的注意力均有限。

因此每轮审核不得机械执行一个无限增长的大型 checklist。

每次审核应首先确定：

> 当前最重要的 3～5 个问题是什么？

并优先投入审核资源。

超过核心问题范围的新观察，如果：

- 不影响当前阶段目标；
- 不属于安全硬不变量；
- 不属于直接回归；

应降为：

```text
P3 / Follow-up
```

而不是继续扩张当前 blocker 集。

---

# 8. 审核严重度

PRA 继续使用：

```text
P1
P2
P3
Merge Gate
```

但严重度不再只表示安全问题。

---

## 8.1 P1

任何足以使当前阶段不能宣称完成的问题，包括：

### P1-Business

- 核心业务路径无法完成；
- 普通任务可能永久停留在非终态；
- 用户完成必要操作后业务不能继续；
- 常见异常只能通过重新创建业务对象绕过；
- 页面声称某能力可用，但实际上只能查看、不能完成业务。

### P1-Safety

- 越权；
- 重复副作用；
- UNKNOWN 误处理；
- 数据双权威；
- 并发导致不可恢复错误；
- 高风险操作缺失必要门禁。

### P1-Efficiency

仅在严重影响可交付性的情况下使用，例如：

- 正常操作需要不合理的多次人工重复确认；
- 一个常见局部故障使整个系统长期停止；
- 设计复杂度已经严重阻碍当前开发；
- 为简单业务引入明显不可维护的架构。

---

## 8.2 P2

有明显业务、安全或维护影响，但存在合理临时路径，且不阻止当前阶段核心目标。

---

## 8.3 P3

- 文档元数据；
- 非关键 UX；
- 可延期审计增强；
- 不影响当前业务目标的维护改进。

P3 不阻止合并。

---

## 8.4 Merge Gate

仅用于客观交付门禁，例如：

- CI 失败；
- build/package 失败；
- migration/health gate 失败；
- 必须的 smoke test 失败；
- 必须的外部验收证据缺失。

`Merge Gate = 0` 不等于业务目标成立。

---

# 9. 双结论制度

以后任何较大实现 PR 的最终审核必须给出两个独立结论。

## 9.1 Implementation Review

```text
P1 = X
P2 = X
Merge Gate = X
```

回答：

> 当前实现有没有明确代码/合同 blocker？

---

## 9.2 Stage Goal Validation

必须单独给出：

```text
PASS
FAIL
NOT YET VALIDATED
```

回答：

> 当前阶段承诺给用户的能力是否已经得到足够证据证明？

因此合法结论可能是：

```text
Implementation:
0 P1 / 0 P2 / 0 Merge Gate

Stage Goal:
NOT YET VALIDATED
```

这时不得宣称阶段整体完成。

---

# 10. 冻结 blocker 的正确使用方式

首次实现审核完成后，可以冻结 blocker 集，以保持开发收敛。

冻结以后：

- 不随意加入新的同层问题；
- 修复后只复核原 blocker 与直接回归；
- 不因为模型又想到另一种理论风险就扩大范围。

但冻结 blocker 不得覆盖三种情况：

1. 修复直接破坏硬安全/数据不变量；
2. 修复使阶段核心业务目标失效；
3. 新证据证明原审核基础事实错误。

这三种情况属于真实例外，而不是普通 scope expansion。

---

# 11. 开发效率必须成为正式审核维度

审核不仅要问：

> “安全吗？”

还要问：

> “为了做到这一点，代价合理吗？”

典型应指出的问题包括：

- 用第二套状态机解决已有状态机可表达的问题；
- 为一次简单恢复建立大量通用基础设施；
- 正常业务频繁触发 fail closed；
- 一个 SKU 的问题阻塞整个无关业务域；
- 用户必须重复创建本可恢复的任务；
- 一项维护动作需要大量人工 CLI；
- 同一事实被多个模块重复计算和保存。

安全设计如果使系统实际上无法运营，也是不合格设计。

---

# 12. 业务生命周期责任原则

跨组件业务对象应满足：

> **任何非终态状态都必须存在明确的当前责任主体。**

审核时不需要为每个 PR执行大型 checklist，但必须能够回答：

```text
现在是谁负责？
下一步是什么？
什么条件触发下一步？
如果失败怎么办？
如果重启怎么办？
最终由谁收尾？
```

如果答案是：

- “用户以后再点一次”；
- “下一次任务生成时顺便处理”；
- “Worker 正常应该就行”；
- “另一个服务可能会处理”；
- “页面上还能看到”；

均不能作为完整的后台业务责任。

---

# 13. 测试证据按任务类型匹配

## 总体架构

主要证据：

- 业务旅程；
- 责任矩阵；
- 模块边界；
- 正常/失败/恢复时序。

---

## 模块实现

主要证据：

- 单元测试；
- 事务测试；
- 并发；
- 幂等；
- 权限；
- 直接集成测试。

---

## 集成/Cutover

必须存在跨组件 journey test。

例如：

```text
Create
→ Dispatch
→ Queue
→ Worker
→ Importer
→ Terminal
```

以及至少一个：

```text
Create
→ Blocked
→ Human resolution
→ Re-evaluate
→ Continue / Reconfirm / Terminate
```

和一个：

```text
Create / Prepare
→ process restart
→ persistent recovery
```

不允许以多个互相独立的 Mock 测试替代该证据。

---

## Bugfix

只要求：

- 原问题稳定复现；
- 修复；
- 直接回归；
- 必要的相关集成测试。

不得借 Bugfix 重做整个系统验收。

---

# 14. 常见审核失效模式

以后遇到以下判断必须提高警惕。

### “全部 fail closed，所以安全”

可能意味着：

> 系统从此再也不会继续。

---

### “Queue 已完整测试”

必须先确认说的是：

- Business Task；
- Dispatch；
- ShadowBot File Queue；

哪一个 Queue。

---

### “CI 全绿”

只能证明测试合同成立。

---

### “严格遵守原计划”

如果原计划与业务目标冲突，这不是优点。

---

### “不新增任何状态/表/Service”

只有在现有模型确实能承担业务责任时才是优点。

---

### “这个问题留到后续阶段”

必须证明当前阶段仍然能够独立满足自己的承诺。

---

# 15. Review Stop Rule

审核必须有明确停止条件。

当满足：

1. 冻结 P1/P2 已关闭；
2. Merge Gate 通过；
3. 当前任务类型要求的核心证据充分；
4. Stage Goal 已 PASS，或明确属于 NOT YET VALIDATED；
5. 没有新的硬不变量破坏或直接回归；

审核应结束。

不得为了追求“绝对没有任何问题”继续扩大检查范围。

工程审核的目标是达到足够可信的交付判断，而不是无限证明系统完美。

---

# 16. 标准审核输出格式

以后较大 PR 建议统一输出：

```text
Task Type:
Architecture / Module / Integration / Bugfix

Review Profile:
R1 / R2 / R3 / R4（按实际影响，见第 19 节）

Core Goal:
本阶段要让用户获得什么能力

Review Focus:
本轮最重要的 3～5 个审核问题

Boundary Conflicts:
无 / 列出冲突

Findings:
P1 / P2 / P3

Implementation Review:
X P1 + X P2 + X Merge Gate

Stage Goal Validation:
PASS / FAIL / NOT YET VALIDATED

Efficiency Assessment:
合理 / 偏重 / 需要重新设计

Next Action:
合并 / 修复 / 讨论边界 / 进入集成验收
```

# 17. 对 Task 13 类项目的应用示例

## Task 13 总体规划

重点：

```text
销售自动化真实业务是否完整
数据权威是否清晰
各阶段责任是否连续
模块拆分是否合理
```

不应主要审核具体 POST/SQL/Token。

---

## 7D 库存

重点：

```text
库存唯一权威是否真正建立
销售扣减/恢复是否正确
cutover 是否安全
实现是否过度复杂
```

---

## 7E 控制面

重点：

```text
人工创建、Review、Authorization、Automation
是否形成合理的业务控制面

而不仅仅是：
每个 Service 是否安全
```

如果发现“Task 创建后发送失败无人接手”，应立即认定为业务责任缺口，而不是因为 Authorization 正确 fail closed 就通过。

---

## 7F 集成/Cutover

重点：

```text
一个真实运营任务是否能走完整生命周期
异常后是否能恢复
进程是否真正具备业务能力
运营者是否知道下一步
```

此阶段组件级测试只能作为基础证据，不能替代真实旅程。

# 18. 最终治理原则

PRA 后续审核遵循：

> **大任务审业务逻辑，子任务审实现质量，集成阶段审真实旅程，Bugfix 审直接问题。**

以及：

> **业务可行性、安全正确性、开发效率是同级审核目标。**

以及：

> **阶段边界是服务目标的默认设计约束，不是高于目标的绝对规则。**

当既有边界与真实任务目标发生冲突时：

> **优先显式提出 Boundary Conflict，讨论并修改设计，而不是机械遵守边界一错到底。**

最终审核追求的不是：

> “这个系统找不到任何风险。”

而是：

> **“它能够用合理复杂度完成真实业务，并且在必要的安全边界内可靠运行。”**

## 19. 风险等级与验证投入

Task Type（Architecture/Module/Integration/Bugfix 等）和 Review Profile（R1～R4）是两条轴；文件格式不决定风险。R1：机械文档/展示/低影响纯逻辑；R2：普通只读/解析/业务规则；R3：真实写、授权、迁移、UNKNOWN/RECONCILE；R4：公共合同、权威关系、跨模块责任/恢复架构。

按实际影响选择设计/静态、模块、集成、恢复、CI、实机证据。R4 设计文档不自动要求本地反复全量回归/实机；实际集成仍必须验证同一 Runtime 的真实 journey。仓库 CI 正常运行，不为赶进度绕过已有 Gate。

新增表、字段、状态机、Service、锁、Summary、version、恢复链前回答“不增加会发生什么具体事故”。优先运行约束→人工确认/恢复→复用既有能力→局部校验→必要最小持久结构。对称检查可以删除什么；单机、多平台不自动意味着分布式系统。

## 20. 开发与文档收敛

先以同一个业务对象、同一组日期/单位/数量案例检查正常、失败和恢复，再决定物理结构。尽早通过最薄纵切连接 Web、授权、执行和结果；不能全部模块完成后才第一次验证箭头。

规范与证据按问题分轨：目标看最新业务裁决，现状看指定 SHA 代码，验证看对应范围，部署看现场证据，历史解释当时理由。设计已采纳、实现、部署、验收分别记录；撤回意见退出缺陷输入。

已明确事项不反复提问；影响近期范围/口径/授权的缺项集中裁决，缺少平台证据明确探索门槛，未来非必要问题可延期。Routine 文档路径和措辞由执行者判断，不反复上浮。

每个主题一个主要定义处，README/AGENTS/index/status 作为短入口。治理自身有复杂度预算，不为每个问题建立永久规范/审批。历史证据不改写；可在上层标明角色和替代关系。

独立 cold-start 在正式 AGENTS 已实际生效后，只给 Canonical 阅读集与中性完整情景。评价推理、来源和对未知的诚实表达，不考术语背诵；作者不得模拟独立 AI。先判断误解来自材料、问题还是推理，再修订对应部分。默认一次完整验收加失败项/直接影响复核，关键问题未解决保持未通过，不无限扩题。
