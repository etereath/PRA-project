## 1. 安全边界与证据处理

本轮只执行：

- 进入已经打开的订单管理页；
- 切换当前日期和两个历史日期；
- 等待页面加载；
- 纵向滚动订单列表；
- 查看已捕获的影刀元素及其选择器结构。

本轮未点击发货、退款、确认收货、支付、联系买家或其他订单写操作，未投递
ShadowBot 队列请求，也未写真实 Runtime DB。

页面包含平台订单号、货位号和省份等不应进入公共合同的信息。因此：

- 不把原始页面截图复制进仓库；
- 不在报告、fixture、日志或数据库中转录这些值；
- 已捕获的订单号元素只允许作为探索期页面定位辅助，禁止进入结构化结果；
- 仓库证据只保存脱敏结构事实和外部元素库摘要。

外部 `test2` 元素库 `selectorsV2.xml` 的本轮只读证据摘要为：

```text

sha256 = fb8bb481367962920666cebe4be6fbfef77269bf5c51449e621e08ded8a16b20
```

生命周期文件仍是过期的 `RUNNING` 记录，但控制目录没有新鲜 heartbeat；
`inbox / working / results` 均无活动文件，`stop.signal` 不存在。本轮不把过期生命周期
记录当作 Worker 运行真值，也没有启动第二个 Worker。

## 2. 已确认的页面能力

### 2.1 当前日期可查询

2026-07-31 当前日期可以在日期选择器中选择。页面加载完成后明确显示：

- 四项零值汇总；
- “暂无订单”空状态；
- 无订单卡片。

因此，“当前日期不可访问”这一旧假设与本轮实测不符。当前能力候选值应为：

```text
supports_order_scan = true
supports_current_trade_day = true
supports_historical_trade_day = true
```

但“可读取当前交易日截至观察时刻的快照”不等于“当前交易日已经结束并可最终结算”。
公共合同需要把以下两个维度分开：

```text
read_capability = AVAILABLE
trade_day_finality = OPEN | CLOSED
```

当前交易日在 18:00 截单前只能形成带 `observed_at` 的进行中快照；不得把空结果解释为
完整交易日最终销量，也不得在 18:00 前进入 `FINAL` 日结。

GitHub Issue #20 正文目前仍声明
`supports_current_trade_day=false`。该 Capability 属于父 Issue 冻结边界，必须先更新
父 Issue，再修改公共实现和验收矩阵；本报告只记录实测冲突，不静默改写权威范围。

### 2.2 历史日期可查询

本轮重复读取了两个相邻历史日期。两天均能返回：

- 日期级汇总；
- 多张订单卡片；
- 精确到秒的下单时间；
- 列表尾部的明确结束标记。

同一历史日期在切换离开后再次进入，卡片内容和时间降序顺序保持一致。该结果可以作为
“页面顺序在本轮样本内稳定”的证据，但还不能证明跨版本或并发新增数据时顺序永远稳定。

日期选择器能滚动显示相邻年份、月份和日期，但本轮没有证明后台可访问的最早和最晚
业务日期。选择器出现某个年份不等于该年份一定存在可查询订单。

## 3. 列表、滚动与结束标记

已确认页面结构为：

```text
固定日期入口
→ 日期级汇总
→ 单列订单卡片
→ 纵向滚动加载
→ “没有更多了”结束标记
```

两个历史样本均观察到：

- 列表按下单时间从新到旧排列；
- 页面底部存在明确“没有更多了”文本；
- 日期级数量等于卡片数量合计；
- 日期级金额等于卡片“合计”之和；
- 日期级均价等于日期级金额除以日期级数量；
- 日期级买家数在本轮两个样本中等于卡片数，但这不足以证明其严格语义是唯一买家数。

本轮所有卡片都只显示一个商品明细。尚未证明平台不可能出现一个订单卡片包含多个商品
明细，因此 Adapter 不得仅凭本轮样本永久冻结“一单一行”。

可信完成条件建议冻结为：

```text
目标日期仍等于 requested_platform_trade_date
AND 页面不处于加载态
AND 所有已加载卡片通过字段关联校验
AND 明确观察到“没有更多了”或可信空页“暂无订单”
```

只因为“下一条元素定位失败”不能认定扫描完成。

## 4. 页面字段与公共合同判定

### 4.1 可以进入后续脱敏 fixture 的候选字段

| 页面标签或结构 | 本轮格式 | 候选公共语义 | 当前判定 |
| --- | --- | --- | --- |
| 日期选择值 | `YYYY-MM-DD` | `platform_trade_date` | 可冻结 |
| 等级 | 等级文本 | `grade` | 可冻结 |
| 商品名 | 品种文本 | `platform_product_name` | 可冻结 |
| 下单时间 | `YYYY-MM-DD HH:MM:SS` | `order_created_at` | 可冻结，时区按平台本地时间 |
| 数量 | 正整数，单位“扎” | `ordered_qty` 候选 | 页面格式可冻结，业务口径待确认 |
| 第 N 次购买 | 正整数 | `purchase_sequence` | 可冻结；无买家身份时只能做订单占比 |
| 新用户/回头客/铁粉买家 | 枚举标签 | `buyer_segment` 候选 | 页面可得，是否入 v14 待评审 |
| 待质检/待结算 | 枚举标签 | `order_stage` 候选 | 页面可得，不等同付款状态 |
| 单价显示 | 十进制金额 | 未命名候选 | 不得先命名为实收单价 |
| 合计 | 十进制金额 | 未命名候选 | 不得先命名为 `seller_received_amount` |
| 日期级均价/买家/数量/金额 | 汇总值 | 批次对账证据 | 可用于完整性复核，买家语义待确认 |

Issue #20 将页面金额预先定义为 `seller_received_amount`，但页面实际标签只有“金额”、
“单价”和“合计”。本轮无法仅凭页面标签证明这是已结算卖家实收，而不是订单应收或其他
展示口径。因此，在平台业务说明或结算页交叉证据出现前：

```text
seller_received_amount = NULL
```

结构化原始结果可以暂用明确的 Adapter 局部名称
`displayed_order_total_amount`，但不得让该临时名称直接进入公共 v14 事实。

同理，页面只显示一个数量字段。本轮没有取消、退款或部分履约样本，无法证明它同时等于
`ordered_qty` 和 `effective_qty`。取消量继续保持：

```text
effective_qty = NULL
cancelled_qty = NULL
cancellation_derivation_method = ""
```

### 4.2 明确禁止持久化的页面信息

- 平台订单号；
- 货位号；
- 省份；
- 搜索框输入；
- 买家身份、联系方式、地址或聊天内容；
- 原始页面正文和未脱敏截图。

独立规格文本本轮可见，但父 Issue 已明确“不采集独立规格字段”。Adapter 可以用它做
同卡片结构校验，不得将其写入公共订单观察表。

## 5. 影刀元素覆盖与“步长 9”假设

已捕获的关键元素包括：

- 订单管理入口；
- 日期级订单数量和销售金额；
- 订单滚动容器；
- 首张卡片的购买次数、等级、品种、数量、单价和下单时间；
- 年、月、日选择器及确认、取消按钮；
- 订单号元素（仅定位辅助，禁止输出）。

目前尚未独立捕获：

- 卡片“合计”金额；
- 买家分层标签；
- 订单阶段；
- 日期级均价、买家数；
- “暂无订单”和“没有更多了”结束标记；
- 第二张及后续卡片的对照元素。

首张卡片已捕获字段在选择器链中的卡片内索引包括 `2 / 3 / 5 / 6 / 7`。用户已做过
初步测试，后续订单对应元素的候选步长为 `9`。本轮将其记录为：

```text
candidate_row_stride = 9
confidence = PROVISIONAL
```

在正式 Adapter 中不得把 `9` 当作无条件常量。冻结前至少需要：

1. 在连续三张卡片上分别验证品种、等级、数量、金额和时间；
2. 滚动一次后重复验证，排除虚拟列表重排；
3. 在另一个历史日期重复验证；
4. 对每个候选卡片执行同卡片字段关联校验；
5. 只以可信结束标记终止，不以索引失败终止；
6. 结构变化时返回 `PARTIAL` 或 `FAILED`，不得错位拼接字段。

优先实现容器枚举；只有影刀接口无法枚举子卡片时，才使用
`base_index + row_no * 9` 的平台专属回退策略。

## 6. 已冻结与待冻结事项

### 6.1 首轮可以冻结

- 当前日期入口可选择并能返回可信空页；
- 历史日期可以返回结构化订单卡片；
- 列表使用纵向滚动，不是页码分页；
- 历史列表存在“没有更多了”结束标记；
- 空页存在“暂无订单”标记；
- 下单时间精确到秒；
- 数量单位为“扎”；
- 历史样本按时间降序；
- 订单 ID、货位号、省份和 PII 不进入公共结果。

### 6.2 仍阻塞公共核心或平台 Adapter 的事项

- 父 Issue 中 `supports_current_trade_day=false` 与实测冲突；
- 页面“合计”是否等于卖家实收；
- 单一数量字段与 `ordered_qty / effective_qty` 的映射；
- 取消量是否只能长期保持未知；
- 一个订单是否可能包含多个商品明细；
- 相同规范业务字段的真实重复卡片样本；
- 最早/最晚可访问业务日期；
- “步长 9”在跨滚动、跨日期条件下的运行时验证；
- 脱敏结构化 fixture 及其 schema/hash。
