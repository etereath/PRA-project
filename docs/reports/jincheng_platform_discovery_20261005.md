## 商品读取与写入语义

### 2026-11-18 商品列表复核

工作台版本为 **4.5.0**。商品管理的搜索为空，等级、分类菜单均选中“全部”。全部页显示 33 项，首批读到 20 张卡片，滚动补载后读到 21 张，截图确认底部显示“已经到底了～”。出售中标签显示 4 项，切入后截图和无障碍文本均只有 2 张卡片及同一尾标。两个范围都存在计数差异，原因未确定。重新选“全部”时先短暂出现零行，随后回到 20 张首批卡片和“上拉显示更多”，所以过渡零行也不能作盘点结果。检查结束已恢复全部范围。

4.5.0 还出现独立的“待激活”标签、卡片状态与“激活”按钮，待激活商品可有正库存。出售中卡片可能同时显示售罄且仍可下架，出售中筛选也不能替代全商品范围。列表卡片主价格原样保留为展示价格，已命名的补贴、平台售价和结算价分别保留。

新增 [锦成商品读取核心](../../app/adapters/jincheng_products.py) 及注入桌面读取端口。11月18日的实现曾用括号数字校验覆盖，21 张的脱敏回放因此返回 `PARTIAL / PRODUCT_COUNT_MISMATCH`。11月19日负责人确认这些标签计数有误，商品数量以实际读到的卡片为准。现行读取核心要求端口确认范围和筛选，校验卡片、累计补载和显示身份，并比对可见尾标处的两次连续读数。标签数字变化、偏大或偏小不影响数量或完成判定。

共享 Windows 驱动和进程控制实现存在于 MP-RO1 本地提交 `5b48701`，当前 [PR #70](https://github.com/etereath/PRA-project/pull/70) 的远端版本仍为规划。接入开发者应在共享驱动基线可供集成后接通端口，取得独立 Windows 扫描与来源绑定证据。正式 `LISTING_STATUS_SCAN` 目前校验在线/待上架双页及采集流水、结果哈希、映射。接入开发者需要依据已有来源绑定合同设计锦成输入，交由正式 Importer 验证，避免把单页尾标冒充双页完成或让未见商品被当作下架。成交明细的完成证据仍独立待补。

### 身份与单位

商品卡片包含花材名称、等级、成熟度、每扎支数、枝长/长度区间；“支/扎”和“枝/扎”两种文字均出现，长度有 `≥`、区间和 `CM` 等表示。未读到稳定商品 ID。商品可定位性暂由页面显示组合支持，**同名同级是否可能存在多个规格仍未证实**。

建议继续使用 `platform_name + platform_product_identity → internal_sku`。稳定 ID 若后续可获得则优先使用；没有 ID 时须核验候选商品唯一性及规格，不沿用其他平台同名同级的 SKU 推断。歧义应在读取/写入前失败，不增加 account/session/page 认证系统。平台自身的子账号标识和收益权限不构成 PRA 新增多账号模型的理由。

### 价格

列表同时存在卡片主价格、平台补贴（元/扎）、平台售卖价、结算价、竞争价格以及价格排名。accessibility 可把主价格拆成 `¥`、整数、小数三个文本节点；按全页第一个数字或第一个人民币符号提取会误取。

本轮对有补贴商品进入编辑，确认其**供货价与该商品列表结算价相等，平台售卖价另列**；这只是所查看样本的关系，不能外推所有渠道的统一结算公式。未来 UPDATE_PRICE 首先明确管理者要改的字段是供货价；平台售卖价、补贴、佣金、成交合计和最终净结算不得互相替代。

### 上下架、售罄与数量

- “已售罄”与“已下架”可同时出现；各标签不是互斥枚举。
- 本轮还实际观察到在售商品数量变为零后标为售罄，但仍保留“下架”按钮；零库存不等价于显式下架。
- “已下架”商品可以有正库存。不能以数量正负单独推断 online/offline，也不能以“出售中”集合覆盖全部平台已上架商品。
- 平台库存先视为可售数量候选，不能直接当 PRA 实物库存；自动售罄后的可售/展示语义仍需独立定义。
- 库存快捷弹窗有明确“确定”，编辑商品也有库存字段。后续改价若整表提交，必须证明不会把过时库存、媒体、退货策略等无关字段写回；本轮没有请求体证据。

### 编辑及隐藏门禁

实际编辑页观察到必填标识、最多 8 张图片、最多 1 个视频、“退货转代卖”的说明。该说明表示不合格退货可能由质检重新定级定价后转代卖，不能将其当普通价格选项切换。

列表/编辑的 accessibility 还包含价格偏离市场均价、禁售、图片未更新、超过30天未更新、转代卖会清库存并下架等提示模板。部分模板含 `undefined` 或上一商品名称，截图中并未呈现对应弹窗。这些只能作为**待验证门禁线索**，不能宣称本轮触发过，也不能自动点击其中的确认文本。

## 成交、营业日与履约

### 读取路径与字段映射候选

可靠入口候选为“销售统计 → 选择日期/渠道 → 各花材等级 → 详情”。底部“自营订单”在本登录态是 NFC 入位，不能按名称直接选为 ORDER_SCAN。

| UI 字段 | 既有 OrderObservation 候选 | 约束 |
|---|---|---|
| 下单时间 | `order_created_at` | 保留完整时刻，时区配置需按锦成核验；不截断成归属日 |
| 花材、等级 | `platform_product_name`、`grade` | 规格歧义必须处理，C+/D+/O 不擅自折成 C/D/0 |
| 行内数量（扎） | `order_qty` | 不是每扎支数、买家数或订单数 |
| 行合计（元） | `order_transaction_amount` 候选 | 先核实补贴/优惠/售后含义；不把结算净额或当前供货价乘数量当原成交额 |
| 统计页所选日期 | `requested_platform_trade_date` / 来源日期候选 | 目前 UI 表达送货日期；需确认与 PRA 平台交易日的对应关系 |
| 本次采集时刻 | `observed_at` | 由采集器记录，不能用下单时刻或历史日期冒充 |

上述是适配候选，不是已经创建的 DTO、配置或 Runtime mapping。

### 日期和完整性风险

1. 当日送货的成交详情实际包含前一晚下单记录，证明下单自然日不能直接作为这组订单的归属日。
2. 历史日期查询有效，但单品详情标题仍写“今日成交明细”；上层“今日送货/明日送货”快捷计数也不随历史日期同步为该日计数。应绑定所选日期、渠道与行内容，不能抓标题作为日期真值。
3. 明日按钮明确切到次日，出现零汇总和最终空态。需等加载完成后同时核验日期、渠道和空态，不能只见零行就接受。
4. 历史单品详情滚到底后，已读取行数/数量/合计与页头摘要可相互核对，但未见明确终止标志；也未验证大量订单分页、同秒相同订单重复、换货及所有渠道覆盖。**成交完整扫描未通过证明**，不能直接标记 ACCEPTED。
5. 成交行未见稳定订单 ID；货位号可能为“待分配”，客户名为简写，二者都不应当作订单唯一键。既有 fingerprint + occurrence 能力应优先评估，不能新增一套以客户资料为核心的身份系统。
6. 本轮商品销量、可售数量、排行和工作台汇总自然变化；来源未冻结，不同时间页面汇总不能强求完全相等，也不能把后读事实覆盖旧观察。

#### 2026-11-19 今日需送货与明日需备货

核对 MP-RO1 当前示例配置、现场验收配置及该工作区的锦成归档。两份配置均选「今日送货」。归档中 6 次部分采样都绑定 2026-10-07 送货日，另有 3 次同范围失败记录，所以这批归档未计入「明日需备货」的交易。采样入口是销售统计的自营汇总，工作台数字和逐笔交易另有各自口径。

复核时的采样器每轮只请求一个范围，支持单独选择「明日送货」。对于「今日送货」和「明日送货」，Reader 按上海日期核对实际所选送货日，JSON 用 `requested_range` 保存请求，`range_text` 保存页面确认的日期。文件按采集日期归档。

结合 F2 工作区现行《业务合同》第3节、第10.4节和第11节，项目用平台规则确定销售日。日内累计按同销售日与同覆盖择一接管，历史订单负责独立日结。蚂蚁花团在18:00换销售日，午夜切换明日备货与今日供应的读取来源。锦成已证实送货日可包含前晚下单，仍需确认本平台销售日界和两档的累计覆盖。

## UI 自动化可行性与 HTTP API 边界

### 已证实的 UI 行为

- Windows 能单独定位“锦成入驻商家”窗口，与其他供应商小程序区分；多数文本和输入框可被 accessibility 读取。
- 大列表出现 `child_limit` 截断；整页 `document_text` 有时能提供更多行，但也包含隐藏模板和后台保留的上一页面。输入框聚焦时，`document_text` 甚至只返回查询词，不能把它当恒定结构的全页数据源。
- 部分页面返回后/异步加载后元素索引变化；本轮一次返回点击因索引失效被工具拒绝，刷新后用新索引正常返回。索引不能持久化为 selector。
- 普通输入能完成中文查询；一次 accessibility `set_value` 清空未反映到可见输入框，随后通过确认焦点、全选、退格、Enter 成功恢复。工具返回成功不等于页面状态已经改变。
- 列表长滚动需要观察实际进展；一次很大的滚动量并未直接抵达末尾，End 键也没有让列表跳到底。
- 商品列表终点、异常列表终点、订单明细无终点、NFC/售后/统计空态以及收益权限错误需分别处理。

建议把窗口/导航/可见区域/行定位/输入校验留在锦成专属 Reader/Executor，业务层继续消费标准事实。这里的定位是 Adapter 实现细节，不新增公共 page identity proof。

### 尚未获得的 HTTP 信息

`servicewechat.com/.../page-frame.html` 只是微信容器，不是业务 HTTP API。本轮未获得业务域名、method/path、请求/响应 schema、稳定商品/订单 ID、鉴权续期、分页 cursor、错误码、限流、写请求幂等键或条件更新能力，也未获得服务商正式开放接口文档。

因此交付的是**现场页面接口勘察及 Adapter 接入边界**，不是逆向 HTTP SDK。没有读取凭据、解包客户端、注入调试器、改代理/证书、绕过权限、扫描猜测接口或重放请求。未来若取得正式文档或受控业务请求样本，应只记录去除 token/用户资料后的 schema；供应商支持渠道由负责人决定是否联系。

## 与现有 PRA 能力的复用及缺口

下表源码判断绑定本分支基线 `aaa9349`；不是对其他尚未合并 PR 的审核。

| 能力 | 既有入口 | 锦成所需增量 / 当前限制 |
|---|---|---|
| 商品公共身份 | [platform_product_identity.py](../../app/platform_product_identity.py) | 复用版本化 identity 与 digest；补充稳定 ID 或验证显示身份唯一性，不新增账号维度 |
| 商品事实持久化 | [product_observation.py](../../app/services/product_observation.py) | 复用 importer、source binding、scope/completion 与 mapping；先定义供货价、可售数量、售罄/上下架转换 |
| 订单持久化 | [order_observation.py](../../app/services/order_observation.py) | 复用 batch、requested date、金额/数量、fingerprint/occurrence、原子导入；确认送货日与交易日关系 |

| 写执行与恢复 | [shadowbot_executor.py](../../app/services/shadowbot_executor.py)及现有 Task / operation / attempt / lock、v4/v5、Worker / Importer | 将来增加平台专属 Executor；保留持久授权、写前读/expected old、唯一提交/写后读、UNKNOWN/唯一 RECONCILE，不另建 Queue 或服务 |

**具体设计边界缺口：**现有蚂蚁订单 Adapter 的非空 ACCEPTED 要求 `scroll_completed && no_more_marker_visible`；锦成已查看的单品成交明细没有可见 no-more 标志。直接把“滚不动”或“有汇总”填成 `no_more_marker_visible=true` 会伪造证据，可能把漏单当完整销售事实。

最小处理是先保留 PARTIAL / UNAVAILABLE，不改现有安全门禁；后续寻找可证明完整性的真实来源。若只能使用“所有单品逐页读取、行数/数量/金额对账、确认无加载与明确遍历终点”的替代证据，须先用非生产样本证明其充分性，并明确调整公共完成合同的必要范围。不能在此次探索中偷偷放宽成“有数字就成功”。

本轮没有新增表、持久字段、Service、Queue、状态机、账号体系或生产 Parser。现有能力的主要缺口在平台 Reader、页面字段语义和完成证据，尚无需要扩建基础设施的具体事故证据。

## 锦成 Light Scan 与 Full Scan 流程复核

本节对照 F2 工作区2026-10-14负责人确认的 [业务合同 §6.2](../business_contract.md#62-light-scan-与-quick-derived) 和现行读链。项目 Light 交叉读取今日供应和上架中商品列表。销售日切换窗口的当前累计由合格的备货来源接管。Full 独立读取上架中与待上架的完整范围。两种扫描均逐页取得独立观察区间，一轮各读一次。历史订单归 Closing，走独立的日期与完成条件。

### 每轮从工作台出发并回到工作台

1. 持有既有桌面 UI 租约，确认锦成窗口、前台和活动 `Page-Frame`。如果停留在别页，先通过底栏进入「工作台」。回读工作台正文中的「今日需送货」与「明日需备货」后才开始本轮，底栏「工作台」文字本身不足以确认所在页。
2. 每次导航或滚动前重新定位活动页中的控件，操作后等待加载并稳定回读。每个范围记录选中标签、实际日期（销量页）、读到的行或卡片、完成证据、观察起止时间。切换日期标签、重新抓 UIA 树、回工作台再打开列表，单独都不能证明平台数据已重新加载。日期或内容疑似陈旧时，使用已验证的刷新入口并回读范围与内容。无法证明已刷新时，将这次读取保留为诊断证据。
3. 完成读取后点底栏「工作台」，回读并确认同样的正文标志，再释放租约并发布本轮合格结果。可安全导航的读取失败也执行同一返回步骤。焦点丢失、意外窗口变更、租约丢失或无法确认工作台时立即停止输入并标记本轮失败，保留能解释失败的只读证据。由下次持租约的操作者恢复并确认工作台后重新开始。这项工作台起止规定也适用于两档诊断、跨日复核和 Closing。

### Light Scan

1. **工作台 → 销售统计 → 自营 → 经确认的当前累计范围。** 页面顶部「今日送货」「明日送货」是实际采样的两档，工作台卡片「今日需送货」「明日需备货」的口径还需对照验证。检查所选送货日期、渠道、累计覆盖、稳定商品行、数量单位、汇总和终点。按平台规则把合格来源绑定到目标销售日。两档均可用于跨日取证，同一送货日的合格累计按覆盖和时点择一接管；切换或刷新证据不足时保留上次合格累计及其时效。
2. **商品管理 → 经完整性验证的在售商品范围。** 读商品身份、当前直接展示的价格及其口径、平台可售量、上架事实。保留结算价、平台售价、补贴等不同字段，按实际卡片数计数。先核对「出售中」是否覆盖仍上架的售罄商品。如果只能由「全部」完整覆盖这些商品，先以实机验证卡片状态能够识别完整在售集合。
3. **返回工作台并确认。** 用已验证的商品身份、规格及单位关联两页。销量行可独立保留，无法唯一映射的行保留聚合和缺失原因。两页分别记录时间，价格从商品列表直接读。任一必需范围无法完成，本轮不发布合格的 Light Scan 结果。

### Full Scan

1. **工作台 → 商品管理 → 完整读取上架中和待上架范围。** 共用 Light 的商品列表读取逻辑。可先使用「全部」作为实机候选，清空搜索、选全部等级和分类，累积补载至可见尾标并稳定回读，按卡片证据识别在售、售罄、下架及待激活。单独验明「待激活」与项目「待上架」的映射。记录实际卡片数和未知状态，括号数字不参与覆盖判断。
2. **返回工作台并确认。** 正式运行沿既有 `LISTING_STATUS_SCAN`、v5 只读快照及 Importer/ProductObservation 提交，绑定父运行、采集尝试、真实范围、结果摘要和商品映射。现有 Importer 要求两个业务范围各有完整性证据。若采用「全部」派生两组，先证明两个范围的覆盖及状态映射，再确定所需的最小接入适配。未知状态、缺尾标或覆盖不足均拒绝本轮正式导入。

锦成接入开发者负责接通 Windows 导航和读取端口，下一次手动实机验收分别记录两种扫描的工作台起止、页面范围和合格输出。验证11:00候选时刻时，切换前后各做一轮。每轮从工作台开始，经微信菜单「重新进入小程序」确认窗口重建并重新定位工作台，然后回读两档的实际日期和自营商品行，最后各自回到工作台。按同一实际送货日比较累计范围。上游现行实现的默认节奏是 Light 每10分钟、Full 每小时 `HH:10`。锦成当前只做手动复核，验收后再单独确定运行配置。

## 锦成跨日订单扫描（Closing）

按项目[历史日结](../business_contract.md#11-daily-sales-closing独立历史日结)和[失败处理](../business_contract.md#12-closing-失败重试与维护边界)复用同一业务链。Closing 读取已结束、已冻结的目标平台交易日的逐笔订单。日内累计继续由指定销量来源提供。现有 F2 日结处理器的 19:00 规则和作业配置绑定蚂蚁花团。锦成须先确认自己的销售日边界、该交易日对应的送货日期和历史来源冻结条件，再接上同一运行与恢复链。11:00 的候选切换时间与工作台 17:55 提示各留作待验证的平台线索。

### 一轮操作

1. **绑定目标日期。** Closing 父运行显式给出上一已结束的锦成 `platform_trade_date`，由已确认的平台规则映射到应选的送货日期。重试和维护沿用各自明确指定的目标日。现阶段可用指定送货日期做只读诊断。
2. **工作台 → 销售统计 → 左上角日期选择器。** 按工作台共同规则确认起点。确认选择器中的年、月、日后提交选择，等加载结束，回读左上角实际送货日期、选中渠道和稳定汇总。基线候选为「全部」，须验证它与各独立渠道的覆盖关系。保留上层商品组与渠道、品种、等级、规格、单位的绑定。快捷两档的括号数字与详情标题中的「今日」都可保留为诊断文本，日期和覆盖以实际所选范围及其内容为准。
3. **逐组进入「详情」，返回统计页复核范围。** 只取当前活动 `Page-Frame`。遍历各组完整订单卡片，记录下单时刻、品种、等级、规格、渠道、数量、金额、可读复购序号和明确的零量零额退款。页头订单数、销量、换货量和金额按各自口径核对卡片，详情返回后重验所选日期、范围和当前商品组，再继续下一组。结合分页或视口衔接证据保留真实的重复卡片，由既有 fingerprint + occurrence 处理相同指纹的多次出现。新客户或复购文字只有在序号语义可确认时才映射；买家简写、地区和货位无需采集。
4. **验收整轮并回到工作台。** 非空必须依次证明目标日及渠道完整、商品组无漏读、组内可验证终点，以及按已核实的数量和金额口径对账。明确空态须同时满足冻结目标日期、该渠道覆盖完整、实际界面稳定显示无记录且相应汇总为零。若存在明确退款明细，仍走非空流程并保留在来源资料中。可安全返回时经统计页和底栏回到工作台，回读正文后释放 UI 租约。选日错误、跨页范围变动、加载失败、缺终点、对账失败或未确认工作台收尾时，保留诊断并拒绝锁定该日。

### 导入、重试与维护

- 合格结果使用既有 Closing 父运行和 `ORDER_SCAN` 子运行，绑定平台、目标交易日、实际页面日期、采集批次、读前读后时间、范围与终点、内容哈希。通过 `OrderObservationImporter` 原子导入后核验冻结日、来源资格、运行绑定和哈希，按平台/交易日锁定一次。导入后回执丢失时先查原批次并恢复锁定，避免重复读取或重复入账。历史日结的事实进入历史查询，库存扣减与当前销量仍走各自的既有入口。
- 在正式接入后，首轮失败沿既有 Run 和 Outbox 记录故障，同一个目标日最多自动重试一次。第二次失败进入 Closing S2 与人工复核，由运营负责人从历史日结维护入口处理。已锁定来源的修正由管理员显式发起，绑定原来源、操作者、理由及幂等键。当前锦成仍为手动只读验证。
