- 报告日期：2026-07-23
- 适用平台：蚂蚁花团供应商微信小程序
- 实施载体：PRA 任务中心、SQLite、ShadowBot/影刀 `test2`、本地文件队列
- 文档性质：开发总结与审查输入，不是审查结论

后续交接整理（2026-07-23）：当前入口、合同、归档和审查步骤已汇总到[任务12最终交接报告](task12_final_handoff_20260723.md)。本报告继续保留开发过程、问题回溯和防复发经验。

## 1. 结论摘要

任务12已经完成从“已验证的单商品改价”到“任务中心驱动的多商品正式 COMMIT 队列”的核心开发，并通过多轮真实小程序验证。最终链路具备以下能力：

- 从任务中心读取同一平台的完整改价任务列表。
- 每项正式业务输入只依赖内部 SKU、旧价格和目标价格；平台由批次指定。
- 通过“商品资料与库存录入”把内部 SKU 解析为页面商品名称和等级。
- 一次创建并投递一个包含全部商品的 v4 COMMIT 请求，不再按商品分别投递命令。
- Worker 在任何改价动作前主动刷新并读取当前“上架中”页面，按“商品名称 + 等级”唯一匹配全部目标。
- 根据页面实时位置从上到下编排执行顺序，不依赖任务输入顺序，也能跳过中间的非目标商品。
- 在整个批次进入写操作前校验所有目标的页面旧价；任一旧价不一致即以 `OLD_PRICE_CHANGED` 安全停止，且不提交任何商品。
- 严格串行修改价格；第 4 行及以后商品根据实际可点击区域滚动，不通过误点击后再滚动来试错。
- 每个商品提交后独立重新定位并回读，只有实际价格等于目标价才记为 `VERIFIED`。
- 回传当前商品页面的完整价格、库存和在售状态，而不只回传被改价的商品。
- Result Importer 校验请求、结果、哈希、逐商品绑定和计数恒等式后，回写任务、批次账本和平台状态表。
- 支持长驻 Worker；普通连续任务不再重复启动和关闭影刀，结束时通过 `stop.signal` 正常返回并执行末端 `关闭.flow`。

最近一次暖态四商品真实验证的总耗时为 `51.094 秒`，四项全部 `VERIFIED`。本报告仅说明开发成果和现有证据；任务状态仍应保持原状，等待审查方检查代码、文档和实机证据后决定是否通过。

## 2. 本次任务的目标与边界

### 2.1 实际完成目标

本次开发没有另起一套改价逻辑。最终实现以已成功验收的批次 `BATCH-T12-OPTIMIZED-COMMIT-20260721-02` 为业务动作基线，保留其已经证明可行的弹窗打开、价格填写、确认、提交和回读链路，只在其前后补齐正式批次所需能力：

1. 正式任务输入和 SKU 映射。
2. 整页预扫描、全目标唯一匹配和旧价总门禁。
3. 按实时页面行号编排执行计划。
4. 单次投递的 v4 多商品合同。
5. 批次账本、逐商品结果、完整页面快照和数据库回写。
6. 长驻 Worker 生命周期和运行性能记录。

### 2.2 明确不属于本任务的内容

- 上架、下架和“不再上架中”页面的跨页面对账，由任务13处理。
- 第二个平台适配和跨平台混合批次。
- AI 自动生成价格、自动审批或自动绕过旧价核验。
- 支付、订单和资金操作。
- 以视觉识别替代结构化商品身份匹配。

### 2.3 授权口径

开发和实机验收阶段，创建可执行 COMMIT 队列前需要展示固定清单并取得明确批次授权。正式运行阶段不再依赖 Codex 对话中的临时“用户确认”；production profile 以发布前再次校验通过的 `pending update_price` 任务作为执行权威，并继续执行 SKU 映射、旧价一致性、合同哈希、幂等和结果回读等系统门禁。

## 3. 最终端到端流程

```text
任务中心提供完整 update_price 任务列表
→ 校验平台、SKU、expected_old_price、target_price
→ 从 products.xlsx 将 SKU 唯一解析为商品名称 + 等级
→ 创建一个 v4 COMMIT 批次合同并投递一次
→ Worker 主动刷新“上架中”商品页
→ 按结构化索引读取当前页面所有商品及价格、库存、状态
→ 按商品名称 + 等级唯一匹配批次全部目标
→ 校验所有目标均存在、均唯一、旧价全部一致
→ 按当前页面实际行号从上到下生成执行计划
→ 逐商品严格串行：定位、必要滚动、打开弹窗、核价、填写、提交
→ 每项提交后独立重新定位并回读实际价格
→ 回传逐商品结果和当前页面完整状态快照
→ Result Importer 校验请求/结果/哈希/计数/绑定
→ 更新任务状态、批次账本和 listing_status
→ 失败或 UNKNOWN 时停止剩余项目，并按副作用边界处理
```

这个流程不依赖商品固定排序。页面行号只是在当次预扫描后生成的临时执行信息，不进入任务输入或授权合同。

## 4. 主要开发成果

### 4.1 正式任务和合同贯通

- 正式任务使用任务中心已有的 `internal_sku`、`platform_name`、`expected_old_price` 和 `target_price`。
- 删除了对 `listing_status_id`、快照版本、READ_ONLY attempt 和 `read_batch_id` 的 COMMIT 前置依赖。
- 旧价安全不依赖数据库快照锁定，而由 Worker 在写操作前读取页面实际价格并比较。
- 一个批次只生成一个带完整 `items` 数组的 COMMIT 请求。
- 请求包含批次、执行尝试、指令和逐项绑定信息；Importer 不接受绑定不一致的结果。

### 4.2 SKU 和页面身份统一

- 商品映射的正式来源改为“商品资料与库存录入”工作簿 `data/samples/products.xlsx`。
- 页面本身不提供可直接读取的 SKU，因此 Worker 不按 SKU 点击页面。
- PRA 先把 SKU 映射为商品名称和等级；Worker 再以结构化的“商品名称 + 等级”唯一定位。
- 视觉识别只作为人工观察或异常诊断，不能决定业务身份。

### 4.3 多商品预扫描与执行编排

- Worker 首先读取当前页面的所有商品，不按任务目标逐个重复枚举页面。
- 商品名称使用 `wx-view index = 1, 17, 33, 49...` 的等差索引规律；同一行的等级、价格和库存使用已验证的结构化字段偏移读取。
- 所有目标均唯一存在且旧价全部一致后，才进入写操作。
- 执行顺序按当前页面行号从上到下生成，既减少滚动，也避免依赖任务创建顺序。
- 正式样本已覆盖“跳过中间商品”和第 4 行以后商品。

### 4.4 COMMIT 安全边界

- `OLD_PRICE_CHANGED` 在任何商品提交前阻断整个批次。
- 弹窗打开后再次核对商品身份和价格，避免列表定位与弹窗身份脱节。
- 每项提交后独立回读，不用目标价或输入框回读冒充平台最终结果。
- 提交后结果未知时停止批次，剩余项目为 `NOT_ATTEMPTED`，不得自动重试 COMMIT。
- 批次和逐项均保留 `side_effect_state`，区分尚未写入、已提交、已验证和未知。

### 4.5 完整页面状态回传

早期结果只回传被修改商品。当前实现会同时回传预扫描得到的完整页面状态：商品名称、等级、价格、库存和 `ONLINE` 状态。

Importer 使用该快照更新当前平台状态表。页面商品能在库存主数据中唯一匹配但状态表没有记录时，会新增对应状态记录；只有库存主数据中不存在的页面商品才报告 `UNMAPPED_PRODUCT_DISCOVERED`。任务12只同步当前“上架中”页面事实，不把未出现商品擅自判定为下架。

### 4.6 READ_ONLY 效率修复

READ_ONLY 已与目标清单解耦，只负责读取当前页面。结束判定由旧的“三次相同指纹”改为：

1. 按等差索引枚举商品。
2. 下一个索引不存在且页面出现“没有更多了”时立即结束。
3. 只有没有结束标记、仍可能延迟加载时才滚动。

实机结果由 `46.686 秒、3 次扫描` 降为 `27.445 秒、1 次扫描、0 次滚动`。旧的 `16.228 秒` 样本使用的是目标字段读取策略，不能直接当作当前完整页面快照的同口径性能目标。

### 4.7 长驻 Worker 和影刀生命周期

- `test2` 支持常驻队列监听，普通连续任务不再执行“检查—启动—运行—关闭—再检查”的完整循环。
- 生命周期记录保存在队列控制目录，记录上次状态、最后执行 ID、处理计数和窗口状态。
- 只有修改 `test2` 本身、达到运行上限或记录状态与实际状态不一致时才重启影刀。
- 正常结束使用 `stop.signal`；Worker 无活动请求时返回，主流程等待 1 秒后调用末端 `关闭.flow`。
- 不再依赖外部工具能枚举 `RobotRunnerView`，因为该窗口在当前环境中可能不可见。

截至本报告生成前，生命周期记录为 `STOPPED`，最后执行 ID 为 `ATTEMPT-52710408e5e1488a`；`inbox/working/results` 均为空，`stop.signal` 不存在。

## 7. 开发过程中踩到的坑、根因和修复

### 7.1 没有先锁定成功基线，重复开发已验证功能

**现象：** 在单商品改价已经稳定后，又重新引入 READ_ONLY、fresh READ 和 FILL_PREVIEW 作为批次开发主路径，重复验证已经成立的能力，消耗大量时间。

**根因：** 开始任务12时没有把“最后成功 COMMIT”和“最后成功 READ_ONLY”的代码、合同和实机证据冻结成明确基线，也没有限制本阶段允许修改的函数范围。

**解决：** 明确以 `BATCH-T12-OPTIMIZED-COMMIT-20260721-02` 为 COMMIT 动作基线，以 `ATTEMPT-T12-LOGIN-FAST-READ-20260721-01` 为读取基线；恢复已验证读取函数，后续只增加整页预扫描、匹配、编排和 v4 合同。

**下次避免：** 每项新任务先建立“黄金基线卡”：代码哈希、成功 Run ID、输入、输出、允许修改点、禁止重写点。新实现若需要偏离基线，必须先列差异和理由。

### 7.2 把“批次扩展”做成了“重新设计整条链路”

**现象：** 本来只需把成功的单商品动作放进队列，却一度同时改动读取、预览、合同和执行器，出现问题时难以判断是哪层回归。

**根因：** 缺少分层实施顺序，多个变量同时变化。

**解决：** 按“恢复动作基线 → 只生成执行计划但不提交 → 接入 v4 单次队列 → 真实提交 → 优化性能”的顺序重新推进。

**下次避免：** 每一阶段只改变一个可验证边界；先做结构化 dry-run，再开放副作用。不要把架构升级、性能优化和 UI 选择器重写放在同一轮。

### 7.3 静态选择器与业务值耦合，且对旧链路的判断不准确

**现象：** 一度认为旧弹窗身份选择器写死了捕获时的业务值，并据此推断只有某个等级能通过；但既有多商品实机证据与该推断冲突。

**根因：** 没有先逐字段区分选择器中的结构属性、运行时索引和业务文本，也没有对比最后成功版本的实际调用链。

**解决：** 先回到成功版本，逐函数比较当前代码；页面身份统一由结构化“商品名称 + 等级”读取和核对，业务值不再作为不可变捕获常量使用。

**下次避免：** 选择器变更前先制作属性表：哪些字段是结构约束，哪些字段会随商品变化，哪些仅是捕获样例。任何“选择器已失效”的结论必须同时解释历史成功样本。

### 7.4 误报 Python 运行版本

**现象：** 报告写影刀使用 Python 3.10，分析中又以“实际 Python 3.7”为理由移除 `slots=True`，口径矛盾。

**根因：** 把开发机解释器、影刀模块管理界面和实际 Worker 解释器混为一谈，没有以运行时 `sys.executable` 和 `sys.version` 为证据。

**解决：** 后续兼容性判断改为以影刀实际运行输出为准，不再从界面配置或语法报错反推版本。

**下次避免：** 每次同步后首轮诊断结果必须记录解释器完整路径、版本和代码文件哈希。没有这三项时，不得在报告中断言运行版本。

### 7.5 中文编码规则只存在全局指导，项目内约束不足

**现象：** 中文日志、JSON、Markdown 和 PowerShell 边界出现乱码风险，项目文件没有给后续执行者足够明确的约束。

**根因：** 依赖 Codex 全局指导，影刀、PowerShell、Python 和文件落盘并不会自动继承同一编码设置。

**解决：** 强化项目 `AGENTS.md`：源码和 JSON/Markdown 显式 UTF-8，CSV/TSV 使用 UTF-8-SIG，Python 文本读写显式 `encoding`，中文文件写后回读；控制台只作显示，JSON 文件才是数据真值。

**下次避免：** 把编码检查作为提交门禁，而不是出错后的排障步骤。每次跨进程传递中文时优先传文件路径和哈希，不从控制台复制回业务文件。

### 7.6 SKU、平台名称和状态表曾存在多套临时口径

**现象：** 任务中心的正式 SKU 与开发阶段临时 SKU 不一致；艾莎 B 状态表仍保留旧 SKU；静态 JSON 映射缺少卡布奇诺 E，导致正式任务在本地构建阶段被阻断。

**根因：** 任务、状态表、静态映射和库存主数据同时充当身份来源。

**解决：** 以任务中心的 SKU 和规范平台名称为输入，以 `products.xlsx` 为 SKU→商品名称/等级的唯一映射来源；状态表中的 `internal_sku` 只作为追踪引用，业务唯一键使用平台+品种+等级。

**下次避免：** 一个字段只能有一个事实来源。临时映射文件必须标记为测试资产，不能作为正式任务默认参数；任务执行前自动检查库存主数据的 SKU 覆盖率和重复页面身份。

### 7.7 对 COMMIT 增加了无效的快照过度约束

**现象：** 曾要求任务携带 `listing_status_id` 和快照版本，导致任务中心字段与当前流程不匹配。

**根因：** 试图用数据库快照锁替代平台页面提交前核价，但平台商品列表只能主动刷新，正式 COMMIT 本身已经读取并比较页面价格。

**解决：** 从任务输入、授权哈希和 COMMIT 门禁中移除状态行 ID、快照版本、READ_ONLY ID；保留实时 `expected_old_price` 比较。

**下次避免：** 新增安全字段前先说明它防御的具体风险，并确认现有门禁是否已经覆盖。不能证明新增字段提供独立安全价值时，不进入正式合同。

### 7.8 读取曾枚举过多元素并保留旧的三次指纹门槛

**现象：** READ_ONLY 出现无效滚动和点击，完整读取耗时 `46.686 秒`；同一页被扫描三次。

**根因：** 页面字段已经改为完整快照读取，但结束逻辑仍保留旧目标清单时代的“三次相同指纹”稳定性门槛。

**解决：** 使用商品行等差索引直接读取；“下一个索引不存在 + 没有更多了”立即结束，只有无法确认结束时才滚动。

**下次避免：** 改变数据范围时必须重新审查循环终止条件。性能报告至少记录扫描次数、滚动次数、刷新、枚举和总耗时，不能只给总秒数。

### 7.9 第 4 行以后点击失败，最初采用了错误的补救思路

**现象：** 商品超出可视边界时无法打开弹窗；“未出现弹窗再滚动”会误点其他按钮。

**根因：** 将滚动作为点击失败后的补救，而不是定位后的确定性动作。

**解决：** 先通过唯一匹配得到实际行号和元素边界；如果行号或实际 Y 坐标不可点击，先滚动到安全区域，再执行一次确定性点击。

**下次避免：** UI 自动化不得通过点击失败来探测布局。所有点击前先验证目标身份、边界和可点击区域，失败时停在副作用前。

### 7.10 快速路径遗漏了“页面保留上轮滚动位置”

**现象：** `ATTEMPT-354799e7788a4b92` 首个商品卡布奇诺 E 已位于视口上方，快速路径仍直接点击，最终 `ELEMENT_NOT_FOUND`。

**根因：** 优化代码假设每个批次从页面顶部开始，复用了预扫描结果但没有检查当前视口。

**解决：** 批次开始前读取第一目标的实际边界；若顶部行不可点击，先向上恢复视口，再复用预扫描计划。该失败发生在提交前，证明副作用门禁有效。

**下次避免：** 任何缓存或复用都必须列出隐含状态，包括当前页面、筛选标签、滚动位置、弹窗状态和窗口句柄。性能优化必须先通过“非默认状态”回归。

### 7.11 每个商品之间等待过长

**现象：** 四商品队列约 68 秒，商品之间重复执行窗口准备、页面确认和全量枚举。

**根因：** 单商品函数原本为独立运行设计，放入批次后仍保留每项完整初始化。

**解决：** 批次只做一次登录、刷新和预扫描；各商品复用已准备窗口和行计划，提交后只做必要的独立回读。

**下次避免：** 将成本分为批次固定成本和逐项边际成本。扩展成队列时，只有与商品身份或提交结果直接相关的步骤才能留在逐项循环内。

### 7.12 冷态与暖态耗时混在一起

**现象：** 修复后第一轮虽然 4/4 成功，但总耗时 `104.984 秒`，其中预扫描 `50.750 秒`；若只看总时长，会误判优化失效。

**根因：** 影刀/小程序冷启动、登录和页面准备与逐商品执行没有分段统计。

**解决：** 增加 `batch_performance`，分别记录预扫描、每项执行和总耗时；紧接着的暖态样本为 `51.094 秒`。

**下次避免：** 每次性能结论至少包含冷态一轮、暖态一轮和分段数据；两种样本都要保留，不能选择性报告。

### 7.13 影刀每轮都重启，收尾流程复杂且容易出错

**现象：** 频繁执行检查、运行、关闭、再检查；`RobotRunnerView` 又无法被外部窗口枚举稳定捕获。

**根因：** 沿用单次应用运行思路，没有利用 `test2` 的长驻队列 Worker。

**解决：** 增加生命周期状态记录，正常连续任务保持 Worker 运行；仅在代码同步、上限到达或状态异常时重启；收尾统一用 `stop.signal → STOPPED → 关闭.flow`。

**下次避免：** 每轮操作前先读生命周期记录并与队列/窗口事实交叉验证，不因为“外部工具看不到窗口”就直接重启或强杀进程。

### 7.14 早期人工报告不够“人工可读”

**现象：** 报告曾接近代码和 JSON 的堆叠，没有直接说明成功与否、读取了哪些商品、每项结果和简短错误；还把可控歧义测试混入正常流程。

**根因：** 把“保留全部技术证据”误解为“把全部原始字段写进正文”。

**解决：** 报告正文改为自然语言结论、逐商品结果、前后价格、运行 ID、数据库回读、计数恒等式和简短错误；原始 JSON 和哈希只作为证据引用。歧义/重复身份仅属于负向验收。

**下次避免：** 报告先回答五个问题：是否成功、处理了什么、每项结果是什么、失败原因是什么、数据库与平台是否一致。技术原文放附件，不替代结论。
